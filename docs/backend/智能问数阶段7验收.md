# 智能问数阶段 7 验收（本机部署与交付）

> 本文保留首次部署记录。其中“真实业务库”指两表样例库 `askdata_smoke`。随后对自有 `ops_platform` 五张巡检表进行真实模型只读验收，并修复连接池、集合隔离、SQL 路由等问题；当前结果见[阶段七复核与自有库实测](智能问数阶段7复核与自有库实测-20261107.md)。

## 一、结论

平台库已由平台 Alembic 从 `0043_llm_agent_channel` 迁移到 `0049_askdata_stage5`，`askdata` schema 建表 48 张、触发器 48 个，`vector` 与 `pg_trgm` 扩展就位。后端与前端以新镜像重建并切换，`/health/ready` 返回 200，`askdata` 消费者心跳正常。

部署后冒烟 **15/15 通过**（连接、结构刷新、构建、目录、代码依据、发布、问数、导出、权限），旧功能回归 **18/18 通过**（含 `/health/ready`、登录、报告、告警、审计、审批、Agent 配置、模型绑定）。问数在真实业务库上产出可执行 SQL 并返回 1 行结果，金额单位、软删除标记与 30 天窗口三处口径均正确。

部署过程中定位并修复 **6 个真实缺陷**，其中 5 个只在真实构建与真实问数链路上暴露，确定性测试与 mock 通道均未覆盖；另 1 个是模型通道的结构化输出能力差异。功能开关与回退两条路径均已演练，回退约束写入第七节。

未执行的部分集中在「真实业务库规模化」与「浏览器端验收」，见第十节。

问数实际产出：

```sql
SELECT SUM(s.amount_cent) AS total_paid_amount_cent
FROM public.sales_order AS s
WHERE s.status = 'paid'
  AND s.deleted = false
  AND s.paid_at >= CURRENT_DATE - INTERVAL '30 days'
  AND s.paid_at < CURRENT_DATE + INTERVAL '1 day'
```

三处业务口径都被正确采用：金额以分为单位（直接对 `amount_cent` 求和并在说明里指出单位）、软删除列必须排除、时间窗口落在 `paid_at` 而非 `created_at`。这些都是列注释与结构语义推导的结果，未接源码规则。

## 六、部署过程中修复的缺陷

| # | 现象 | 根因 | 修复位置 |
| --- | --- | --- | --- |
| 1 | 构建在 `ingesting_catalog` 失败：`catalog_column` 违反 `catalog_table` 外键 | 上游 `store_factory()` 约定「事务外必须立即提交」，平台实现从不提交；表在主线程、列在线程池，未提交的表行对写列的连接不可见 | `app/integrations/askdata_semantic.py` 增 `commit` 回调；`app/repositories/ontology.py` 执行写后按深度提交 |
| 2 | 构建在写外键时 `ontology_single_insert_required` | 上游把整批外键合成的多行 `INSERT` 一次写入，平台适配层只接受单行 | `app/repositories/ontology.py` 支持多行 INSERT，逐行注入 `model_version_id` |
| 3 | 语义编译读不回已写入的 term（`failed to fetch persisted terms`），向量为 0 | 版本作用域把基表包成子查询，PostgreSQL 的「按主键分组、选同表其它列」只对基表成立，`GROUP BY term.id` 直接 `GroupingError` | `app/repositories/ontology.py` 的 `_expand_group_by`：把已分组表上的选中列补进 GROUP BY |
| 4 | 构建在 `building_metrics` 报 `embedding_empty`（缺陷 3 的后果） | 同上：term 读不出来就没有可向量化的输入 | 同 3 |
| 5 | 问数检索不到任何表，模型编造 `public.orders`，反复重试直到预算耗尽 | 检索侧用标准库线程池并发做向量检索，不复制 ContextVar，池内 `require()` 抛「requires an authorized platform task」，异常被吞后候选为空 | `candidates_retrieval.py`、`candidates_preparation.py` 改用 `host.ContextThreadPoolExecutor` |
| 6 | 语义编译首步即失败：`This response_format type is unavailable now` | 默认通道 `deepseek-flash` 不支持 `response_format=json_schema` | `auto_ontology/utils/llm_invoke.py` 对 DeepSeek 改走 `function_calling`，且不指定 `tool_choice`（思考模式不接受强制选择） |

另有 1 处补齐而非修复：上游的表／列文档向量由 `ingestion_service` 在目录写入后生成，平台直接调用目录层，因此数据层集合一直为空。`app/services/askdata_build.py` 新增 `_index_catalog`，构建后写入 `data_objects_layer`（实测 13 条：2 表 + 11 列），语义集合 12 条（term 与列属性）另由编译阶段写入。

缺陷 1—4 全部只在真实 PostgreSQL 上暴露：单测用 SQLite 语义或 mock store，看不到复合外键、函数依赖与跨线程可见性。缺陷 5、6 只在真实模型通道暴露。

补丁清单已更新：`backend/vendor/auto-ontology/SENTINELOPS_PATCHES.md` 新增「阶段 7 补丁」小节，`SENTINELOPS_UPSTREAM.json` 的 `patched_files` 补入两个检索侧文件，`test_ontology_host.py` 校验通过。

## 七、功能开关

`ASKDATA_PAUSED` 已接入 `compose.yaml` 的 backend 环境变量（默认空，取值 `on`/`true`/`1`/`yes` 视为暂停）：

```
ASKDATA_PAUSED=on docker compose up -d backend
```

实测：

| 动作 | 暂停时 | 恢复后 |
| --- | --- | --- |
| 提交构建 | 409「智能问数已暂停，新增构建与问数任务暂不受理」 | 202 受理 |
| 提交问数 | 409（同上） | 受理 |
| 读取统计／连接／历史 | 200 | 200 |
| 消费者 | 心跳保留，循环空转不领取新任务 | 正常领取 |

开关不删除数据、不改配置、不取消正在运行的任务；恢复只需把变量置空并重启后端。

## 八、回退演练

演练按「保留旧镜像 + 兼容旧版本」的方式执行，不删除任何 `askdata` 表。

| 步骤 | 结果 |
| --- | --- |
| 重打 `sentinelops-backend:local` 为 `rollback-20261107-stage7` 并启动 | 容器重启循环，日志 `BACKEND_WORKERS must contain unique supported worker names` |
| 收窄为六类消费者后启动 | `live=200`，`ready=503 {"status":"not_ready"}` |
| 旧接口抽查 | `/applications`、`/reports`、`/incidents`、`/agent-configs` 均 200；`/askdata/*` 404 |
| 恢复新镜像 | `ready=200`，基础冒烟 18/18 |

两条约束必须写进回退手册：

1. **旧镜像不认识 `askdata` 消费者**，代码回退时必须同时把 `BACKEND_WORKERS`／`PLATFORM_WORKERS` 里的 `askdata` 去掉，否则管理器拒绝启动。
2. **仅回退代码不会让就绪探针变绿**：库已是 `0049`，旧代码期望更低版本，`/health/ready` 会一直 503。可用的回退组合是「旧镜像 + 恢复迁移前备份」，或等待后续版本把就绪探针改成「不低于」语义。

恢复脚本化路径：`docker tag sentinelops-backend:rollback-20261107-stage7 sentinelops-backend:local` → `BACKEND_WORKERS=<六类> docker compose up -d --force-recreate backend` → 需要回到迁移前状态时再 `pg_restore` 备份并 `alembic stamp` 到备份对应版本。演练结束已切回新镜像。

## 十、未执行与限制

1. **真实业务库规模化未测**：冒烟业务库只有 2 表 11 列。构建耗时 14–16 秒，无法外推到百表规模；`add_fks` 的批量写与目录采样的真实开销需在目标库复测。
2. **问数耗时**：单题 83 秒（思考模式逐节点调用），默认 180 秒预算下复杂问题会被判超时。已把预算调到 900 秒验证；是否长期放宽需按目标通道延迟决定，不建议直接改默认值。
3. **重排未启用**：本机未配置重排服务，`execution/test` 返回 409 属预期，检索只走向量召回。
4. **浏览器与桌面端验收未执行**：本轮为接口级冒烟，未做页面点击级验收。
5. **语义外键重叠度探测被跳过**：上游用 `UNION ALL` 套子查询探测语义外键是否有交集，构建侧 SQL 方言（诊断用的窄方言）不支持 `UNION`／子查询，异常被上游捕获并记录为 `skipped`。本次两表只有 1 条声明式外键、0 条推断外键，不影响结果；表多、推断外键多时会少一层剪枝。
6. **冒烟数据未清理**：`askdata_smoke` 库、只读角色、冒烟连接与版本记录仍在库中，便于复跑；投产前应删除连接并 `drop database askdata_smoke`。

## 十一、复现命令

```sh
# 备份
docker exec sentinelops-postgres-1 pg_dump -U ops_platform -Fc ops_platform \
  > .local/backups/ops_platform_$(date +%Y%m%d)_pre_askdata.dump

# 迁移（仅平台库）

# 构建与切换

# 冒烟

# 开关

ASKDATA_PAUSED= docker compose up -d backend     # 恢复
```

本地请求须避开系统代理（`httpx` 用 `trust_env=False`，`curl` 用 `--noproxy 127.0.0.1`），否则 `127.0.0.1` 会被代理改写成绝对 URI 并返回 404。
