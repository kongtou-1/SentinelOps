# QA 巡检启动故障修复与验收

## 故障与原因

任务「QA 回答质量巡检」原执行 `f0f662c6-b5d7-4fbc-836a-76af21dbb9c2` 已读取两条 QA，但两项 Agent 检查均为 `harness_failed`，没有工具调用轨迹。原执行实际在 2026-10-30 22:59:14（Asia/Shanghai）结束，并非持续运行。

Harness 子进程采用不携带平台凭据的环境。此前 `app.integrations.harness` 为导入 `HISTORY_GUIDE` 引用了业务服务 `knowledge.agent_results`，沿模型与数据库包初始化加载 `db.session`，在子进程启动时因缺少 `postgres_password`、`jwt_secret` 失败。父进程收到通用错误，页面又将具体错误折叠，导致用户难以识别失败。

## 修复范围

- 将历史检索提示词提取到无数据库依赖的 `services/knowledge/history_guide.py`，业务服务保留原导出身份。Harness 子进程直接引用纯提示词模块，不向其传入数据库密码或 JWT 密钥。
- 新增回归检查：清空业务环境变量并在临时目录启动子进程，导入 Harness 后断言没有加载 `app.db.session`。
- 巡检覆盖摘要增加 `checks_errors`。执行记录及报告直接说明检查执行失败和报错数量；结果概览默认展示逐项检查表，错误原因在表格内直接展示。
- 不改变历史判定、数据表或迁移；OpenAPI 路由与模型契约保持一致。

经用户确认，仅补齐两项现有配置：

1. 查询「QA 检查结果回写」的 `allowed_body_fields` 增加 `records`。
2. 任务检查项 `check_191d210a` 的 `source_ids` 绑定上述查询。

任务保持暂停，版本由 1 更新为 2。没有修改 Skill、评估标准或启动周期调度。配置变更使原冻结版本无法直接补检，因此保留原错误执行，以新配置手动发起一轮。
