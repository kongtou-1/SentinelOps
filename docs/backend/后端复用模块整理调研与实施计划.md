# 后端复用模块整理：调研、判断与实施计划

调研日期：2026-10-22。分析对象为当前工作目录中的 `backend/app`，未切换到历史迁移文档记载的其他目录。

## 1. 结论

**需要做一轮有针对性的小模块整理。现有分层与业务目录基本合适，优先调整共用能力的归属、拆开职责混杂的文件，再补充依赖检查。**

这次整理的目标是让同一后端内的代码更容易复用、查找和修改。继续使用现有 Python 应用、数据库和 API/worker 部署方式，不增加独立服务、Python 子项目、依赖注入框架或通用仓储基类，也不整体搬成另一套目录。

判断依据有三点：

1. 现有代码已经按 API、服务、仓储、模型、外部适配与 worker 分层，服务内部也已按业务组织。重新做一遍目录划分收益有限。
2. 确实存在“能力已经复用了，但放错位置”的情况：其他业务为了查一条记录而导入资源 CRUD，为了加解密而导入 SSH，为了读取密钥而导入监控配置。这些依赖值得现在处理。
3. 部分相似实现有不同业务语义。整理应保持这些差异，不能以减少函数数量为目标。

成功标准是：调用方能从职责明确的模块直接取得共用能力；共用模块不反过来依赖具体业务流程；对外接口、事务、审批、监控语义和历史数据保持一致。

### 2.3 不应直接合并的实现

**容器 ID 的宽容提取与执行校验。** 源码身份中的解析函数从字符串末尾提取64位 ID，失败返回 `None`；执行模块要求整个输入符合允许格式，失败抛出 `ValueError`。本次使用相同样本核对：带任意前缀的64位 ID 能通过前者，不能通过后者。保留执行模块中的严格校验；不让它调用宽容解析函数，不增加一个带 `strict` 开关的统一接口。

**审批摘要与报告摘要。** 它们都使用 SHA-256，但报告的 JSON 编码显式设置 `allow_nan=False`，审批当前未设置。本次核对 `NaN` 输入时，报告摘要拒绝输入，审批摘要能够生成结果。因此只迁移报告及修复交接已经共用的编码实现，执行模块的摘要继续保留。不得重新生成历史绑定哈希。

**不同探测对象的状态。** LLM 的停用状态是 `disabled`，服务监测使用 `paused`，两者新鲜度参考字段也不同。可以把状态计算从调度代码中移出，但不统一成一个多参数状态计算器。

**业务审计与队列处理。** 审批、报告、源码和修复交接的审计字段、时间线及锁定要求不同；不同 worker 的抢占、恢复和权限检查也不同。本轮保留各自流程，不新建通用审计服务、任务基类或状态机框架。

**已有的共用模块。** 分页、脱敏、Base、时间字段、Prometheus HTTP 适配和服务 Token 会话已经有集中实现，继续直接使用，不再增加一层 `common` 包装。仓储中少量重复查询可在改动所在功能时局部归并，本轮不开展全仓机械改名或封装。

## 4. 建议的小模块形态

沿用当前所有层级，仅做下列局部增补；文件名是实施目标，不是额外引入的子项目。

```text
app/
  core/
    secrets.py                 # 既有 file_secret + 从 SSH 移入的 cipher
    service_auth.py            # 共用服务 Bearer 令牌校验
  repositories/
    records.py                 # 未删除记录查询及既有 add/refresh 操作
  services/
    records.py                 # active_record、save，保留现有 HTTP 与事务行为
    monitoring/
      metrics.py               # 主机/容器/LLM 表达式、metric_availability
      config.py                # 保留规则发布、发现配置与验证
    resources/
      crud.py                  # 保留资源管理及本轮未调整的其他功能
      metrics.py               # 主机、容器指标读取与现有配置状态判断
    llm/
      status.py                # endpoint_status
      probes.py                # 保留探测执行与调度
  utils/
    docker.py                  # 宽容的容器 ID 提取，保留原函数行为
    canonical_json.py          # 报告体系既有 encoded/digest 实现
```

只暴露已被调用方使用的函数，不为每个业务建立 `facade`、`interface`、`base` 或 `manager`。模块内部可以继续使用普通函数。

对外 HTTP 接口、响应模型和鉴权声明不变。内部导入改到新的直接路径；迁移同一能力时同时更新应用、脚本和测试中的调用方，完成后不保留旧业务文件作为长期转出口。已有测试的 monkeypatch 要指向实际使用该依赖的模块，不能为维持旧测试路径而保留多套实现。

## 5. 分批实施

### 第0批：建立可核对的基线

- 仅在当前工作目录实施。当前目录没有 `.git`，修改前创建本次专用源码快照和文件哈希，不将 `.env`、密钥、缓存或历史导出包纳入可分享产物；不擅自初始化仓库。
- 保存当前 OpenAPI、42张表的元数据、24个迁移文件哈希和应用入口清单。
- 使用明确指定的 `_test` 独立测试库，遵循现有 `conftest.py` 运行一次完整后端基线，记录真实失败。历史文档中的“601通过、1失败”不是当前基线，不能直接沿用。
- 对计划迁移的函数保存代表输入的输出，重点覆盖错误详情、指标结果及历史摘要字节。

完成条件：可恢复本次修改，且能够区分已有失败和整理引入的失败。

### 第1批：密钥、加解密与服务令牌

- 保留 `core/secrets.py:file_secret` 的路径读取、最小长度和异常行为，调用方直接使用它。
- 将 `cipher()` 原样迁入同文件，所有非 SSH 调用方改从这里导入。SSH 自身也使用同一实现。
- 将 `service_authorization()` 原样迁入 `core/service_auth.py`，保留常量时间比较、Bearer 格式和错误响应。
- 删除监控配置文件对 `file_secret` 的转出口；其他地方使用 Prometheus 时直接导入已有 `integrations/prometheus.py`。

完成条件：读取密钥和加解密不再需要经过监控配置或 SSH；既有密文可解密，密钥不变，不重加密数据库存量数据。

### 第2批：通用记录访问

- 将 `active_record`、`save` 移入 `services/records.py`；对应的数据访问操作移入 `repositories/records.py`。
- 仓储函数使用明确名称 `get_active`、`add`、`refresh`，仅迁移当前已有的三项操作，不建立 CRUD 类或自动化通用仓储。
- 更新全部调用方，保留404语义、软删除过滤、唯一约束冲突处理及原有 add/commit/rollback/refresh 顺序。
- `save` 只承接目前已经使用它的简单保存路径。复杂业务仍由原服务控制事务；通用记录查询不能替代权限、事故范围或审批检查。

完成条件：其他业务查询普通记录不再导入资源 CRUD；资源管理模块也使用同一组实现。

### 第3批：指标表达式与指标读取

- 将 `metric_expression`、`llm_metric_expression` 和 `metric_availability` 收入 `services/monitoring/metrics.py`，保留表达式、返回字段及就地处理行为。
- 将 `metrics_result`、`unconfigured_metric`、`server_metrics`、`container_metrics` 移入 `services/resources/metrics.py`，改用共用记录访问和既有 Prometheus 适配器。
- 资源路由、诊断工具、服务监测、预测与恢复核验改从能力所属模块导入。监控规则发布继续留在 `monitoring/config.py`，不在本轮重写其流程。
- 保留资源/服务监测的缺失采样、补点和 availability 行为；LLM 指标继续保留自己的非有限值处理及返回结构。短小但语义不同的范围校验保留在调用方，不增加带多个行为开关的统一查询器。

完成条件：共用表达式和数据可用性处理不依赖资源 CRUD、预测任务、规则发布或 worker；诊断读指标不再导入资源写入模块。

### 第4批：状态和纯数据工具

- `endpoint_status` 移入 `services/llm/status.py`，更新探测器、控制台、绑定与监测展示调用方；保留状态值和新鲜度判定顺序。
- 宽容的 `docker_identifier` 移入 `utils/docker.py`；`identity_inventory` 留在原业务模块。执行 Skill 的严格同名函数保持独立。
- 报告的 `encoded`、`digest` 移入 `utils/canonical_json.py`，报告与修复交接直接复用；执行审批的摘要实现保持独立。
- 不把调度、数据库读取、HTTP 请求或业务审核流程放进纯工具模块。

完成条件：状态展示不需要加载 LLM 探测调度代码；共用值处理不依赖源码或报告业务流程；原有编码、哈希和校验结果一致。

### 第5批：依赖约束与整体验收

- 扩展现有架构测试，检查本次新增边界：通用记录服务不依赖资源业务；密钥及服务认证模块不依赖服务层；共用指标模块不依赖资源 CRUD、预测任务、配置发布和 worker；纯工具不依赖数据库、API或服务层。
- 检查应用与脚本中不再通过旧业务路径导入本轮迁移的能力。架构测试同时识别绝对与相对导入，防止换一种 import 写法绕过检查。
- 每批先运行直接相关测试；最后运行一次完整后端测试、Ruff、OpenAPI和模型元数据比较，并检查 API、五个 worker、会话消费及子进程入口。
- 进行本机隔离环境的代表性验证：资源/服务指标、LLM探测、预测、诊断、审批执行、报告和修复交接读取。验证过程使用原有模拟资源和授权边界。
- 更新后端组织文档，说明这些小模块的归属、导入方式、保存函数的事务行为及保留的语义差异。

完成条件：无新增测试失败，接口和元数据一致，迁移历史未改，进程入口与代表流程可用。若出现已有失败，单独给出基线证据；不得通过更新契约快照、放宽权限或跳过测试掩盖差异。

各批独立形成可审查的变更与验证记录。失败时回退对应批次源码；本方案不涉及数据库结构调整，无需设计新的数据迁移。先完成并验收第1、2批，再继续后续批次。
