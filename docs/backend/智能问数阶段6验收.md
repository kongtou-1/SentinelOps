## 结论

- **确定性部分全部通过**：32 条冻结样例自检 32/32、错误口径拦截 18/18、阶段 6 新增 25 项测试、askdata／ontology 回归 148 项、前端 318 项与生产构建。
- **三种方式的真实模型逐题对比未执行**：本机没有可用的模型通道，也没有获得授权的业务库。本次交付的是可复用的对比装置（三模式上下文装配 + 同一判定器 + 离线评分入口）与确定性代理指标（口径覆盖率 0% → 0% → 100%）。真实结果需在有通道的环境补跑，命令见文末。
- **浏览器与桌面客户端验收未执行**：环境内没有可用的浏览器自动化设施。
- 回归中发现并修复一个真实缺陷：`/health/ready` 硬编码迁移版本 `0047`，阶段 4／5 把 head 推进到 `0048`／`0049` 后，任何已迁移环境都会恒返回 503，直接阻断阶段 7 部署。

## 一、冻结样例集

文件：`backend/tests/fixtures/askdata_stage6/cases.json`（`format=sentinelops.askdata.benchmark`，`version=1`）。

| 分类 | 条数 | 覆盖内容 |
| --- | --- | --- |
| `basic` | 12 | 计数、分组、时间范围、Top N、跨表关联、反连接、去重、按天聚合、聚合函数选择 |
| `python` | 10 | app_a 5 条（PAID／`is_deleted=0`／分转元／`created_at`）、app_b 5 条（SETTLED／`deleted_at IS NULL`／金额为元／`paid_at`） |
| `java` | 10 | app_a 5 条（nativeQuery、JPA 枚举、派生查询 `IsDeletedFalse`、单位常量；含 1 条缺口）、app_b 5 条（`DeletedAtIsNull` 等；含 1 条缺口） |

- 每条样例记录 `question`、`provenance`（精确到 `path:line`）、`expect`（`outcome`／`tables`／`sql_all`／`sql_any`／`sql_none`／`certification_in`／`signals`／`gap_terms`）、`reference_sql` 与 `wrong_sql`。
- 20 条口径样例中 18 条标注了口径信号（`status:paid`、`soft_delete:flag`、`unit:cent`、`time:created_at` 等），共 22 个信号／应用。
- 2 条缺口样例（按退款原因、按支付渠道）的列**确实不存在于冻结 schema**，由测试断言保证，避免把"模型不会"误判成"数据缺失"。
- 参考 SQL 与错误 SQL 都是人工确认口径，只用于判定器自检与离线评分，全程不执行。

## 二、判定器

文件：`backend/app/services/askdata_benchmark.py`。判定项：

| 判定项 | 说明 |
| --- | --- |
| 已生成可执行 SQL | 口径样例必须有 SQL，不能只给文字 |
| 引用正确的表 | 表名按词边界匹配，避免 `orders` 命中 `order_items` |
| 包含必需口径片段 / 命中等价口径 | `sql_all` 全部命中；`sql_any` 每组至少命中一个（容忍 `/100` 与 `amount / 100` 等等价写法） |
| 未使用错误口径 | `sql_none` 任一命中即判失败 |
| 引用依据等级符合预期 | 口径样例要求 `certified`／`draft`，缺失即失败 |
| 缺口样例：未臆造缺失字段 + 已澄清或报告缺口 | 出现缺失列即失败；答复必须说明缺什么 |

SQL 归一化统一做小写、去引号、空白与运算符压缩，因此 `is_deleted = 0`、`"is_deleted"=0` 等价，而 `is_deleted = 1` 不等价。

| 自检 | 结果 |
| --- | --- |
| 每条参考口径应被判定器接受 | **32 / 32 通过** |
| 每条错误口径应被判定器拒绝 | **18 / 18 被拒** |

## 三、三种方式对比

三种模式与生产路径 `askdata_query._payload` 的装配顺序一致：`structure`（无业务规则、无补充定义、无代码规则）、`model`（数据库业务模型的术语与补充定义）、`model_code`（再叠加源码抽取的代码规则）。代码规则来自**真实抽取器**对 `tests/fixtures/askdata_stage4/app_a`、`app_b` 的静态解析，不是手写模拟。

### 上下文规模（app_a）

| 模式 | 术语/规则条数 | 证据行数 | 证据字符数 | SQL 示例 |
| --- | --- | --- | --- | --- |
| 仅结构 | 0 | 0 | 0 | 0 |
| 数据库业务模型 | 2 | 0 | 0 | 0 |
| 业务模型 + 代码规则 | 26 | 24 | 2567 | 2 |

app_b 同构：代码规则 42 条，证据 2544 字符。

### 口径覆盖率（上下文中是否真的带上了所需业务口径）

| 模式 | app_a | app_b |
| --- | --- | --- |
| 仅结构 | 0 / 22（0%） | 0 / 22（0%） |
| 数据库业务模型 | 0 / 22（0%） | 0 / 22（0%） |
| 业务模型 + 代码规则 | **22 / 22（100%）** | **22 / 22（100%）** |

这里刻意使用**谓词形状**匹配（`is_deleted = 0`、`deleted_at is null`、`status = PAID`）而不是列名匹配：目录里出现 `is_deleted` 这个列名不构成软删口径。因此 `model` 模式的 0% 反映的是"刚构建完、只有目录语义、尚未配置业务规则的连接"这一真实起点：应用 A 与 B 的库结构完全相同，仅凭结构无法区分 PAID／SETTLED、`is_deleted`／`deleted_at`、分／元，三种差异全部来自源码。

> 说明：如果管理员在「问数设置 → 业务规则／补充定义」中配置了同样的口径，`model` 模式的覆盖率会上升，代码规则的价值相应下降。本次对比固定为"未配置业务规则"的基线，用于衡量代码规则单独贡献。

### 真实模型逐题对比：未执行

计划要求"使用同一模型和问题，对比三种方式，逐题报告结果"。本次只有装置与代理指标，原因与补跑方式如下。

- 未执行原因：本机没有配置可用的模型通道（Agent 通道需真实密钥），也没有获得授权的目标业务库；上游链路在无通道时不产生真实回答。
- 补跑方式：在具备通道的环境按三种模式各跑一遍 32 题，把回答存成 JSON 后离线评分（判定器与本次完全一致）：

```bash
python backend/scripts/accept_askdata_stage6.py --answers .local/stage6-answers.json --write
```

```json
{
  "structure": {"python-a-01": {"sql": "SELECT ...", "text": "...", "certification": "draft"}},
  "model": {"python-a-01": {"sql": "SELECT ...", "text": "...", "certification": "certified"}},
  "model_code": {"python-a-01": {"sql": "SELECT ...", "text": "...", "certification": "certified"}}
}
```

评分输出按模式给出通过数、分类通过数与逐题失败原因；`provenance` 字段固定标注 `deterministic harness`，真实运行需在报告中另记来源，不得与本表混用。

## 四、运行期场景验证

`backend/tests/test_askdata_stage6_scenarios.py`，8 项，全部通过。

| 场景 | 用例 | 验证点 |
| --- | --- | --- |
| 结构变化 | `test_structure_change_blocks_new_questions` | `schema_hash` 变化后提交问题返回 409「结构已变化」，旧版本不被继续使用 |
| 配置变化（停用） | `test_disabled_configuration_blocks_new_questions` | 关闭问数后提交返回 409「已停用」 |
| 配置变化（历史不可改写） | `test_configuration_change_does_not_rewrite_recorded_context` | 修改预算与配置版本后，既有运行的执行上下文逐字段不变 |
| 运行中撤权 | `test_running_query_rechecks_authorization_after_revocation` | 停用账号后 `_guard` 抛 `authorization_revoked`；worker 拒绝装载运行；运行落 `failed`；原令牌查询运行被拒 |
| 进程重启／任务恢复 | `test_worker_restart_interrupts_running_queries_without_replaying` | `running` → `interrupted` + `run_interrupted` + `interrupted_at`；已完成为不受影响；不得重新领取与重放 |
| 并发 | `test_only_one_worker_claims_a_queued_run` | 两个 worker 同时领取，仅一个拿到（`FOR UPDATE SKIP LOCKED`） |
| 断线重连 | `test_reconnect_replays_the_same_events_without_executing_again` | 两次重放事件完全一致、序号严格递增、`after_seq` 续传为空、执行上下文只落一次 |
| 迁移版本变更 | `test_readiness_follows_the_current_migration_head` | 就绪探针跟随 Alembic head；旧版本仍返回 503 |

已在阶段 3 覆盖、本次随回归复验的场景：并发幂等提交、取消与完成竞争、事件序号唯一、长错误码、多轮历史裁剪、SSE 只重放不重查。

**已知边界**：撤权在运行期由"每次存储写"与"每次领取"复核，已发出的单次模型调用无法中断（与阶段 3 的取消限制一致）；本次未构造"撤权恰好发生在模型调用中途"的注入用例。

## 八、失败与限制清单

1. 三种方式的**真实模型逐题结果缺失**，只有上下文覆盖率这一确定性代理指标；不能据此宣称"代码规则使答案准确率提升 X%"。
2. 浏览器与桌面客户端验收（导航、SSE、下载）未执行。
3. 真实业务库联调未执行，样例基于冻结 fixture 与固定 schema，未覆盖字段类型差异、超大表、跨 schema 等场景。
4. 撤权的中途生效只在"存储写／领取"边界验证；进行中的单次模型调用不可中断。
5. 业务分区与标签仍未参与提示词装配，因此不计入口径覆盖率。
6. `model` 模式固定为"未配置业务规则"的基线；已配置业务规则的连接覆盖率会更高，本报告未给出该分支的数字。
7. 跨模块回归存在 5 项既有环境／夹具失败与 1 项顺序敏感用例，建议单独修复后纳入 nightly。
8. 未在业务库应用迁移、未替换运行镜像，部署与回退仍是阶段 7 的范围。
