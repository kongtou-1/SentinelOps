# 服务可观测性实施与验收

2026-10-16。在当前仓库完成资源下钻、关键 API 与多协议探测、真实请求指标、告警事故关联及诊断证据接入。设计依据见[优化建议](资源下钻与API监测优化建议.md)。

## 已实现

- 应用与服务详情增加「服务监测」，分别展示关键 API 业务可用性、容器运行健康和真实流量采集状态。运行实例、显式依赖、LLM 绑定、关联告警与事故可继续下钻，链接携带同一时间范围。
- HTTP 支持 GET/HEAD、经确认无业务副作用的 POST、期望状态码和简单 JSON 字段断言。请求头与请求体加密入库，不回显；响应只保留状态、耗时、摘要和失败字段路径，不存响应正文。
- 平台视角支持 HTTP/TCP/DNS/ICMP；主机视角由所选主机的 Blackbox Exporter 发起 HTTP/TCP/DNS/ICMP。主机 HTTP 本期仅支持 GET/HEAD 状态检查；鉴权、POST、JSON 断言使用平台视角。主机 DNS 显式指定 DNS 服务器，平台 DNS 使用平台解析器。
- 探测首次错峰、并发上限 4，同一监测不重叠、不积压。间隔 15–3600 秒，超时 1–30 秒且短于间隔。采集器失联记为未知；配置变更清空最近结果并更换指标版本，旧成功不能证明新配置正常。
- 主机页按文件系统、磁盘 I/O、网卡查看实体与历史；通过实际挂载路径关联受影响实例。容器页区分单核 CPU 百分比、占宿主机 CPU 比例、CPU 配额使用率及 cAdvisor 内存限制。配额缺失、挂载库存缺失不伪装成零或空列表。
- 服务监测规则绑定具体监测 ID，沿用规则应用、Alertmanager、事故、自动 AI 诊断与恢复核验流程。诊断加入服务探测证据、服务实例、显式一层依赖和 LLM 绑定；只读工具 `get_service_metrics` 仅接受事故范围内的监测 ID。同机部署不会自动认定为业务影响。
- `0022_service_observability` 补建 `llm_service_bindings` 更新时间触发器，不改写已有记录；新表和字段遵循 UTC 时间及软删除规则。

## 使用与升级

1. 按 README 备份数据库和独立主密钥，停止 backend 与 worker，构建镜像并运行迁移。最新版本为 `0022_service_observability`。
2. 在实际部署目录运行 `uv run --project backend --frozen python backend/scripts/init_monitoring.py`，生成包含 `service-probe` 和 `service-traffic` 的 Prometheus 配置。脚本也会重新生成 Alertmanager 配置；已有手工配置应先备份并合并。保留既有密钥与规则文件。
3. 更新并重建 backend、共用后端镜像的 worker、frontend；重新加载 Prometheus。Compose 已设置 `BLACKBOX_URL=http://blackbox:9115`；宿主机开发默认 `http://127.0.0.1:9115`。调度由 API 生命周期运行，沿用单 API 实例部署。
4. 在服务详情添加少量关键 API，选择目标实例、探测视角和断言。POST 必须使用专用、安全测试请求。Admin 管理监测；Operator/Admin 可手动探测；Viewer 可查看。
5. 在告警规则中选择服务指标和监测对象，保存后显式「应用规则」。更换监测目标、断言、凭据、探测来源或真实流量目标后，也应重新应用关联规则。自动诊断继续使用[全局默认与规则覆盖](自动AI诊断.md)，初始关闭。

### 带登录认证的 API

在服务监测的新建或编辑窗口选择平台视角，在独立的「Token 认证」模块选择「配置登录与刷新」：

1. 填写登录地址和登录请求体 JSON；认证接口有额外请求头时填写「认证请求头 JSON」。登录和刷新均发送 POST JSON，地址不携带查询参数或凭据，不跟随重定向。
2. 填写响应字段路径，默认 `access_token`、`refresh_token`、`expires_in`；支持 `data.access_token` 等点分路径。有效期单位为秒，响应未提供时使用配置的默认有效期。
3. 如有刷新接口，填写刷新地址、额外请求体及刷新 Token 请求字段（默认 `refresh_token`）。刷新时自动向该顶层字段注入最新 Refresh Token；刷新响应未返回新 Refresh Token 时保留旧值。
4. 点击「测试探测」。平台先登录并探测目标 API；配置刷新地址时，还会主动刷新并再次探测。刷新测试失败直接显示失败，不以重新登录掩盖刷新配置错误。测试成功后保存，加入当前服务的定时监测。测试会实际调用接口，但不保存草稿、不改变已有监测结果，也不复用正式监测的 Token。

正式监测自动发送 `Authorization: Bearer <access_token>`，覆盖手填的同名请求头。Token 在有效期内复用，到期前刷新；刷新接口拒绝凭据（400/401/403）时重新登录。目标 API 返回 401 时重新获取 Token 并且只重试一次；其他业务错误不触发认证重试。无刷新接口时到期重新登录。整个单次探测流程仍受监测超时约束。

登录凭据和认证配置沿用主密钥加密入库，响应仅返回是否已配置。Access/Refresh Token 只缓存在当前 API 进程内，按监测项及配置版本隔离；修改、删除监测或重启后重新登录。编辑时可保留原认证或选择「不使用自动 Token」清除；「清除配置」同时清除请求头、请求体和自动认证。当前范围为 POST JSON 登录/刷新与 Bearer 认证，不包含 OAuth 跳转、验证码或 Cookie 会话。

### 从被监测主机发起探测

先登记服务器的 `blackbox_exporter_target=host:9115`，使平台能访问该地址；创建主机视角监测后，下载「主机探测配置」，保存为采集器 Compose 同目录下的 `service-blackbox.yml`。在明确授权的 Linux 主机执行：

```sh
docker compose -f collector-compose.yaml --profile service-probes up -d service-blackbox
```

该可选服务使用主机网络，ICMP 需要 NET_RAW。限制 9115 端口只允许平台访问。已有主机 Blackbox 服务时应合并配置并避免端口冲突。监测或来源配置变更后重新下载配置，再重启或重新加载该 Blackbox 实例；模块名称包含配置版本，旧模块不能冒充新配置。平台不会自动上传配置或部署远程采集器。

### 真实请求指标

服务详情「真实流量接入」登记 Prometheus 可访问的 `host:port`，采集路径固定 `/metrics`。HTTP 监测填写与指标一致的路由模板。应用需输出：

```text
sentinelops_http_requests_total{method="GET",route="/work",status_class="2xx",traffic="business"} 120
sentinelops_http_request_duration_seconds_bucket{method="GET",route="/work",traffic="business",le="0.5"} 118
```

直方图还需常规的 `+Inf`、`_count`、`_sum` 序列。服务发现注入 `application_id` 与 `source_epoch`；应用无需硬编码。路由必须是有限模板，不含用户 ID、请求 ID、完整 URL 或凭据。

探测请求带 `X-SentinelOps-Probe: 1`，应用必须将其标为 `traffic="probe"`。平台只用 `traffic="business"` 计算 5 分钟 RPS、4xx/5xx 错误率、P95 和请求样本数，避免探测污染业务表现。`testlab/service/service.py` 已加入该埋点；尚未重新部署运行中的 testlab。

未配置、采集失联、没有请求样本分别显示对应状态，不填充为 0 或 100%。恢复核验必须获得通知结束后、当前配置下的新鲜成功探测；真实流量规则还需有效的新鲜抓取和阈值证据。Alertmanager resolved 本身不等于资源恢复。

## API 与数据

接口均以 `/api/v1` 开头；完整请求和响应见 [OpenAPI](openapi.json)。

| 方法与路径 | 功能 | 权限 |
| --- | --- | --- |
| GET `/service-monitors?application_id=…` | 查询监测 | resources:read |
| GET `/business-services/{id}/observability` | 服务、实例、依赖、告警事故关联 | resources:read |
| POST `/business-services/{id}/monitors` | 新建监测 | resources:manage |
| POST `/service-monitors/test` | 保存前测试登录、刷新及目标 API，不持久化 | resources:manage |
| GET/PUT/DELETE `/service-monitors/{id}` | 查看、更新、软删除 | 读取 resources:read；写入 resources:manage |
| POST `/service-monitors/{id}/probe` | 手动探测 | containers:diagnose |
| GET `/service-monitors/{id}/metrics` | 固定指标即时值或历史 | resources:read |
| PUT `/business-services/{id}/traffic` | 设置或清除真实流量目标 | resources:manage |
| GET `/servers/{id}/probe-config` | 下载当前版本 Blackbox YAML | resources:manage |
| GET `/monitoring/service-probe-metrics` | Prometheus 采集 | 独立 monitoring.token，不接受用户 JWT |

监测字段包括 `application_id/container_id/probe_server_id`、协议与目标、方法与路由模板、DNS 服务器、重要级别、期望状态码、JSON 断言、间隔/超时/启停、配置版本及最近探测证据。输入 `headers/request_body` 省略时保留原加密配置，空对象显式清除；`token_auth` 省略或 null 保留原认证，对象替换，false 清除。响应仅含 `request_configured/token_auth_configured` 状态，不回显凭据。切换为非 HTTP 或主机视角前须显式清除不兼容的加密配置。草稿测试使用同一请求结构，可携带 `monitor_id` 复用已有加密配置，返回成功状态、错误码、HTTP 状态码、耗时和是否测试刷新。

服务指标为 `service_probe_up`、`service_probe_latency_seconds`、`service_probe_success_rate`、`service_probe_stale`、`service_request_rate`、`service_error_rate`、`service_latency_p95_seconds`、`service_request_count`。百分比查询原始值为 0–1，界面转换为百分数。历史需同时给出带时区的 start/end，范围最多 31 天、最多 11000 点；不接受任意 PromQL。

规则、告警事件增加 `service_monitor_id`；事故详情增加 `service_monitors`。服务器增加 `blackbox_exporter_target`，应用增加 `traffic_target/traffic_config_changed_at`。容器指标增加 `container_cpu_host_percent/container_cpu_quota_percent/container_memory_limit_bytes`；容器观测增加挂载库存及来源状态。原有 `container_cpu_percent` 保持单核 100% 语义。
