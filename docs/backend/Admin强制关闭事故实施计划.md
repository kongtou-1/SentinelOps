# Admin 强制关闭事故实施计划

日期：2026-10-14。用户已授权形成计划后直接实施。

## 现有链路与修改边界

事故状态入口为 `incident_api.status`，前端 `IncidentDetail.vue` 另按触发中告警和恢复待核验数量禁用关闭按钮。`recovery.reconcile` 仅对活动事故的已解除告警取得新鲜正常证据，`incidents.recompute` 据此产生已恢复状态。AI 采用只保存正式分析，不参与关闭判断。

Webhook 已将同一告警 occurrence 绑定到原事故；重复通知不会新建事故。新 occurrence 只聚合到待处理或处理中的事故，因此关闭后新的告警仍会进入正常处理流程。执行申请、审批和 worker 派发前均检查事故是否活动。复盘只要求事故已关闭，并从数据库冻结告警、诊断、执行和时间线。

## 实施方案

1. 扩展原状态接口：`status=closed, force=true`，仅 Admin，关闭原因必填。普通关闭维持已恢复或全部告警核验终止后的人工结束条件，已合并事故不允许再次关闭，重复关闭保持幂等。
2. 事故增加一个非空 JSON `closure` 字段，默认空对象以兼容历史数据。保存强制标识、原因、操作人 ID/用户名、关闭时间、关闭时恢复是否已核验，以及各关联告警的状态快照。迁移只增加该列，现有三个 UTC 时间字段和更新时间触发器继续适用。
3. 关闭与时间线、追加审计、待审批/已批准授权失效在同一事务内提交。告警状态、恢复时间和监控规则不被改写，不自动静默。未派发执行继续通过现有 worker 的事故校验阻止；已派发动作不能撤回，继续记录真实结果。
4. 前端显示普通关闭的禁用原因，并为 Admin 提供独立“强制关闭”入口，确认并填写原因后提交。事故详情、列表及复盘显示强制关闭标记。复盘冻结关闭快照，PDF/Word 导出直接显示管理员决定和未核验事实，AI 提示保留该边界。
5. 独立测试库覆盖权限、未恢复关闭、原因校验、幂等和并发、告警状态不变、关闭后重复/新告警、晚到恢复、授权/队列边界、复盘冻结及导出、迁移升降级和更新时间。完成前端类型检查、构建及交互验收。
6. 本机部署前备份并验证业务库，停止相关 worker 后迁移至 `0016_incident_closure`，更新前后端及 worker，核对当前实测资源和事故仍保持原状态。仅在隔离数据上测试强制关闭，不替用户关闭现有事故。

## 验收标准

- Admin 能关闭仍在告警、恢复待核验的活动事故；Operator/Viewer 无法越权强制关闭。
- 关闭是业务处理决定，不产生虚假的资源恢复、告警解除或执行成功。
- 明确记录谁、何时、为什么强制关闭，以及关闭时尚未恢复的证据。
- 关闭不会因后续通知重新打开；同一 occurrence 不重复生成事故，新 occurrence 正常建事故。
- 已审核旧报告快照不变，新报告和导出能追溯强制关闭事实。

## 实施结果

已按以上方案完成并部署到本机，验证及数据保留记录见 [验收记录](Admin强制关闭事故验收.md)。现有实测事故未关闭，是否关闭由用户在平台决定。
