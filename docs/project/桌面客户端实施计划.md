## 目标与方案

保留现有 Web 前端和 Docker 部署方式，新增独立安装、启动和构建的 SentinelOps 桌面客户端。后台服务继续独立运行，桌面端在运行时配置服务地址，修改地址不需要重新打包。

首版按 Windows 10/11 x64 规划，建议使用 Tauri 2。现有 Vue 3 + TypeScript + Vite 页面继续复用；Tauri 负责窗口、网络与必要的文件保存、外链打开能力。Electron 作为遇到明确兼容性阻碍时的备选，不同时维护两套桌面框架。

“另一套桌面程序”按独立工程和安装产物理解：共享业务页面源码，分别构建 Web 和桌面版本。避免复制整个前端后，两个目录分别修复同一业务问题。

```text
现有 frontend/ 业务页面
    ├─ Web 构建 → 原有 Nginx 部署 → 后台 API
    └─ 桌面构建 → Tauri 安装程序 → 用户配置的后台 API

后台 API → PostgreSQL、Prometheus、后台任务及现有集成
```

桌面窗口关闭后，后台监控、巡检和任务继续运行；客户端不承担后台调度职责。

## 工程组织

建议新增以下工程边界，不移动现有业务目录：

```text
frontend/                  # 现有 Vue 页面、业务逻辑及共享适配
  src/
  dist/                    # 保留现有 Web 输出
desktop/
  package.json             # 桌面开发、构建和打包入口
  src-tauri/               # Tauri 配置、Rust 宿主、权限及图标
  dist/                    # 桌面版 Vue 输出，构建生成
docs/project/桌面客户端实施计划.md
```

- 桌面构建复用 `frontend/`，通过独立构建模式选择平台适配和输出位置。
- Web 保留现有路由、同源代理、权限行为及生产构建方式。
- 桌面专用设置与原生能力通过少量明确入口接入；业务组件不散布 Tauri 判断。
- 沿用现有 pnpm 版本并锁定新增依赖；Rust 依赖提交锁文件。不为此搬迁为大型 Monorepo 或整体升级现有前端依赖。

## 服务地址与连接流程

### 用户流程

1. 首次启动进入“连接服务器”，填写地址并测试连接。
2. 连接正常后保存地址，进入原有账号密码登录。
3. 再次启动读取上次地址；首版沿用会话级登录，不增加长期记住密码。
4. 登录页及应用设置提供“服务器连接”入口，可查看或更换地址。
5. 连接失败在当前页面提供明确错误与重试入口；连接中断不直接抹掉用户会话。

界面以“服务器地址”“测试连接”“连接成功”“无法连接”等标签和状态表达，不增加解释性小字。

### 地址约定

首版填写服务根地址，例如 `https://ops.example.com` 或 `http://192.168.1.100:18088`，由客户端统一追加 `/api/v1/...` 和 `/health/...`。地址可在安装后修改，不编译进安装包。

- 允许域名、IP 和端口；规范化末尾斜杠，拒绝嵌入账号密码、查询参数和片段的配置地址。
- 地址配置保存在当前操作系统用户的应用配置目录，不保存到安装目录。
- HTTPS 正常校验证书；HTTP 用于本机或受控内网联调。URL 配置不提供“忽略证书错误”开关。
- 首版以服务根路径部署为约定，暂不支持任意子路径前缀。安装包不包含生产服务地址、凭据或 API Key。

### 通信实现与服务切换

桌面优先验证 Tauri 原生 HTTP 通道，在现有 API 客户端入口切换传输实现，复用认证、错误处理及 SSE 解析。服务地址的动态配置必须与原生网络权限一起实现，不能为每个新域名重新编译。

先用小范围验证固定具体实现：确认所选 HTTP 插件在锁定版本下支持增量读取、取消、下载及运行时目标约束；若插件权限模型不能满足已配置服务的约束，再采用必要的薄 Rust 封装，不维护两套网络实现。若最终采用 WebView Fetch，须明确记录并实现后台允许的 CORS 来源、方法、请求头与下载响应头配置。

原生层限制请求发送至当前配置的后台服务；跨来源跳转不能携带登录令牌。网络失败不自动重发写操作，保持现有认证刷新语义。

更换服务器时退出旧登录，取消本地在途请求与 SSE，清理旧服务页面数据和认证状态，再连接新服务。晚到的旧响应不能写回新会话，旧令牌不能发送给新服务。断开客户端连接不调用后台任务取消接口，后台任务按原规则继续。

## 实施阶段与完成标准

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| 1. 桌面骨架与通信验证 | 核验 Windows 构建环境；创建 Tauri 工程；打包本地页面；验证可配置地址、健康检查、登录及 SSE | 打包后的窗口可连接隔离后台，AI 流式内容逐段显示，能中断连接；切换服务无旧令牌串用 |
| 2. 双端构建与请求适配 | 固定网络实现；接入地址持久化、连接页、认证刷新、健康接口和错误处理；分离 Web/桌面输出 | 同一套页面可分别构建，两端请求行为正确；更换 URL 无需重打包 |
| 3. 桌面交互适配 | 适配 Hash 路由、刷新恢复、项目介绍与资源中心、外部链接、文件保存、窗口缩放和高 DPI | 内部导航留在应用内；外部链接进入系统浏览器；下载可选保存位置且取消无副作用 |
| 4. 业务与故障验收 | 在独立测试数据下检查权限、核心模块、AI 诊断、巡检、导出、断网恢复及服务切换 | 核心流程可用，权限和审批边界不变；断网不重放写请求；后台任务不依赖客户端存活 |
| 5. 安装与交付 | 构建 Windows x64 安装程序；验证安装、启动、覆盖升级、配置保留与卸载；补充文档 | 交付可安装的 `setup.exe`、构建与配置说明、验收记录；在无项目开发环境的 Windows 用户环境验证启动 |

阶段 1 先解决网络与流式兼容性，再展开其余页面适配；发现明确的框架阻碍时记录证据，再评估 Electron，避免先复制整个前端。

首版使用常规系统窗口，保留现有业务布局，修正桌面尺寸下的溢出和操作入口。托盘、开机启动、系统通知、自动更新与 macOS/Linux 安装包不纳入本期交付。

## 验证清单

- Web 回归：在 `frontend/` 运行现有测试和生产构建，核对原有路由契约、API 代理及登录行为。
- 桌面基础：校验 URL 解析与拼接、配置读写、首次连接、401 刷新、退出、切换服务与旧响应隔离。
- 流式连接：验证中文分块、长连接、客户端取消、服务端中断、认证失效及按现有序号恢复事件；必须观察到增量响应，不能用一次性返回冒充流式通过。
- 文件与导航：验证 API 导出、CSV、本地生成的巡检证据、中文文件名、保存取消、外链和应用内独立页面。
- 业务抽查：以 Viewer、Operator、Admin 核对资源、告警事故、预测、巡检、诊断、审批执行及复盘的可见性与关键操作；写操作使用隔离数据及本机授权目标。
- 安装验证：Windows 10/11 x64；覆盖 WebView2 已存在和需要安装的场景，记录需要网络的安装步骤。若目标需要离线安装，再交付包含离线 WebView2 运行时的安装包。
- 实际桌面验收必须在打包后的程序中进行，开发模式或浏览器通过不能替代安装包验证。
- 如实施确需修改后台，遵循后端规范并显式使用名称以 `_test` 结尾的独立测试库；不对业务库运行测试。

## 后台配置与交付边界

用户后续负责部署独立后台、配置客户端可达的服务地址，以及需要时的域名、HTTPS 或 VPN。该服务入口须开放现有 `/api/v1/` 与 `/health/` 路径，并正确转发 SSE。可直接沿用当前 Nginx 服务入口，即使日常只使用桌面端。

桌面安装包包含本地 UI，不依赖访问远程网页才能显示登录与连接界面。客户端只访问后台 API；数据库、监控组件及服务凭据继续由后台管理。客户端与后台按匹配版本交付，遇到明显的接口不兼容须明确反馈，不伪装成连接成功。

本次规划不部署远程后台或申请域名，不改变服务器、采集器或既有审批执行权限。正式分发所需的代码签名在具备签名材料后配置；未签名测试包应在交付记录中注明。
