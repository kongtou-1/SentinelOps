# Beszel 设计借鉴：监控增强首批

本批保留 FastAPI、PostgreSQL、Prometheus 与 Vue，增强服务器接入、容器健康、人工排障和图表可信度。没有新增业务表，没有复制上游源码。Prometheus 35 天原始历史保留策略不变。

## 使用方法

1. 创建服务器资产，打开服务器详情中的“监控接入检查”。Admin 可下载采集器 Compose；按目标 Linux Docker 服务器的实际条件核对挂载与镜像，部署后将资产中的目标地址配置为 Prometheus 可访问的地址。下载不会自动部署远程采集器。
2. 检查 node_exporter、cAdvisor、可选 Docker 状态采集器及 HTTP 探测的接通状态、最近采样、失败原因与下一步操作。HTTP 探测明确标注平台视角。
3. 同步容器后，在容器详情查看持续健康状态。Operator/Admin 可打开“查看 Docker 状态”“查看近期日志”。Viewer 能查看健康指标，不能调用诊断 API。
4. 新增健康告警时选择 `container_unhealthy`，阈值设为 `0`。`1 > 0` 表示健康检查失败；`0` 表示明确通过。启动中、未配置 HEALTHCHECK、停止、未知或采集失效均不输出此二值指标，不作为恢复证据。
5. 多序列图表可选择具体磁盘、网卡或容器序列，默认最多显示前六条。无效值和查询步长内的缺失点显示断线，真实零值保留。监控暂停、未配置、无数据和历史尾部过期分别显示。

Docker 健康检查失败和容器是否运行是两种独立状态。业务规则仍需通过“应用规则”发布到 Prometheus；新增健康指标不会自动创建规则。健康告警、事故聚合与恢复核验沿用现有链路。每轮有界恢复检查为最近结束且有规则快照的事件保留一半名额，覆盖采集恢复后的再次核验；其余名额按最久未检查时间处理历史积压。恢复必须具有当前采集配置下、通知结束之后的新鲜正常证据，缺少样本不会恢复事故。

## API

| 方法与路径 | 权限 | 返回与约束 |
|---|---|---|
| `GET /api/v1/monitoring/servers-summary?server_ids=UUID&server_ids=UUID` | resources:read | 1–100 个 ID，只返回未软删除资产；每台的 metrics 与 collectors。所有启用服务器共享至多 6 次并发 Prometheus 请求；全暂停/空资产不查询。当前配置的 source_epoch 用于排除旧配置样本。 |
| `GET /api/v1/containers/{id}/health` | resources:read | status、availability、sampled_at、reason。健康状态含 healthy、unhealthy、starting、none、stopped、unknown。 |
| `GET /api/v1/containers/{id}/diagnostics?kind=state\|logs` | containers:diagnose（Operator/Admin） | 绑定数据库资产中的 Docker ID、服务器及固定 SSH 公钥。只读取 State 或最近 15 分钟、最多 200 行日志；16 KiB 输出限制、脱敏、截断标记和固定错误码。无任意命令参数。 |
| `GET /api/v1/servers/{id}/collectors-compose` | resources:manage（Admin） | 原有下载接口现在提供文件名。 |

摘要返回 `server_id`、`metrics`、`collectors`。metrics 包括 `target_up`、CPU、内存、磁盘，磁盘取有效分区最大使用率。collectors 包括 node、cadvisor、docker-state、blackbox。各项包含 availability（available/unavailable/unconfigured/paused/stale）、value、sampled_at、reason；collector 另有 target。采集失败时 CPU 等值为空；确认失败的 target_up 为 0，未发现或过期时为空。单项查询失败不会清空其他指标。

常规抓取的新鲜度上限 60 秒。Docker 状态内部 5 秒轮询、15 秒失效；Prometheus 按 15 秒抓取，API 和告警容许最近 Engine 轮询距查询最多 30 秒，并校验抓取状态，避免正常抓取间隔被误报为过期。健康状态独立于重启/OOM 的完整 5 分钟事件窗口。

资源历史查询返回 `start`、`end`、`step`、`last_sample_at`。每条已有有效序列按请求时间网格补 null；历史尾部超过 max(60 秒, 2×step) 无有效值时 availability 为 stale。CPU/网络等派生指标也通过相应 up 状态过滤，避免采集失败后继续展示旧速率。不会插值或将缺失值替换为 0。

## 部署与验收

本批无数据库迁移。更新 backend、各 worker、frontend、docker-state 镜像；prediction-worker 包含新健康指标的恢复核验逻辑，需要同步更新。远程 Docker 状态采集器若使用旧镜像，也需在人工授权后更新；未更新时页面显示未知，而不推断健康。

```powershell
$env:POSTGRES_DB='ops_platform_test'
$env:REPORT_FONT_FILE='D:/research/contest/.local/report-font/wqy-zenhei.ttc'
& backend/.venv/Scripts/python.exe -m pytest backend/tests -q --tb=short
Remove-Item Env:POSTGRES_DB
Remove-Item Env:REPORT_FONT_FILE
pnpm --dir frontend test
pnpm --dir frontend build
& backend/.venv/Scripts/python.exe backend/scripts/accept_monitoring_enhancements.py
```

本地 Docker 验收使用 `backend/monitoring-enhancements-test-compose.yaml` 的独立临时目标和采集器，验证运行中健康失败→真实 Prometheus/Alertmanager 告警→事故→采集失联仍待核验→恢复健康与采集→新鲜证据确认恢复。结束后关闭已恢复事故，软删除临时资产与规则、重新应用规则并移除临时容器；证据保留于 `.local/monitoring-enhancements-acceptance.json`。

本批没有实施维护窗口、通知渠道、GPU/LLM 绑定、多协议网络探测、出站采集、SMART、systemd 或 OIDC；这些保持为后续独立批次。没有真实外部模型或外部邮件验收。

最终测试结果、真实故障时间线及已知既有测试问题见 [监控增强验收](监控增强验收.md)。
