# Backend 容器合并与部署

## 运行布局

API 与 operations、prediction、source、inspection、ai、report、askdata 七类消费者共享 Backend 容器，内部保持八个独立进程。审批执行 `execution-worker` 独立，脚本巡检的 `inspection-sandbox` 按需独立运行。数据库任务、审批绑定、审计、单实例锁与各类中断恢复沿用原逻辑，不增加 Redis/Celery。

| 模式 | 常驻容器 | 启动方式 |
| --- | ---: | --- |
| 完整平台 | 7 | `./deployment/Start.ps1` |
| 增加脚本巡检 | 8 | `./deployment/Start.ps1 -InspectionSandbox` |
| 增加脚本巡检和本机采集 | 11 | `./deployment/Start.ps1 -InspectionSandbox -LocalCollectors` |
| 临时邮件测试 | 在选定模式上增加 1 | 另加 `-MailTest` |

完整平台为 frontend、backend、postgres、execution-worker、prometheus、alertmanager、blackbox。本机采集为 node-exporter、cadvisor、docker-state；模拟业务、持续流量、SSH 靶机及巡检验收数据源不随主平台启动。

这是容器合并，Python 进程数量仍保持，内存节省应实测。API 与后台任务共享容器资源和部署周期；API 及后台进程日志均出现在 Backend 日志中。

## 启动和升级

在项目根目录执行，先按 README 准备 `.env`、监控配置、独立密钥及本地向量模型：

```powershell
./deployment/Start.ps1 -InspectionSandbox -LocalCollectors
```

脚本执行配置校验和构建，启动 PostgreSQL、导出数据库备份到 `.local/deployment-时间戳/database.dump`，检查活动执行任务，停止旧 API 与七类消费者，再次确认执行队列为空后停止执行进程。随后运行 `migrate` 和 `prepare-volumes` 一次性任务，成功后启动常驻容器。初始化任务使用 `run --rm`，不会留下常驻初始化容器。

迁移只作用于平台库（`POSTGRES_DB`）。智能问数的目标业务库只做元数据读取与采样，不在其上执行任何 Alembic 迁移；`askdata` 的表与索引全部建在平台库的 `askdata` schema 内。

存在活动审批执行时拒绝切换。切换过程中若检测到新执行，API intake 已停止，等待执行结束后重新运行脚本；不强制中断远程动作。任何步骤失败都停止后续步骤，不绕过迁移或健康检查。备份目录含业务数据，不提交或对外分享。

`-NoBuild` 使用已构建的镜像；`-LocalSources` 附加 `compose.sources-local.yaml`，须配置有效的 `SOURCE_INPUT_ROOT`。本地源码只读绑定现在挂载到 Backend。源码存储和归档卷允许 Backend 写入，密钥与向量模型仍只读，Docker socket 仅提供给独立采集器和沙箱，不挂入 Backend。

Linux 或手工部署的同等顺序为：先构建，停止旧写入进程并备份，再执行下列命令。已有活动执行时应先等待完成。

```sh
docker compose up -d --wait postgres
docker compose run --rm --no-deps migrate
docker compose run --rm --no-deps prepare-volumes
docker compose --profile monitoring --profile execution up -d --wait
```

仅执行 `up` 不会迁移或初始化新卷。沙箱需附加 `-f compose.yaml -f compose.inspection-agent.yaml --profile inspections`。停止某一可选模式须显式停止对应容器，省略 profile 不会停止已经运行的服务。

## 进程管理与健康

入口为 `python -m app.cli.runtime`，管理器只启动固定的 API/消费者模块，不接受任意启动命令。默认启动七类消费者，可通过 `BACKEND_WORKERS` 选择逗号分隔的子集；同时调整 `PLATFORM_WORKERS` 使系统页的预期消费者与实际启用项一致。`execution` 不允许并入此入口。

生产 API 固定为一个 Uvicorn 进程；不在 FastAPI lifespan 中重复启动消费者。每类消费者使用自己的 Session 和原有 PostgreSQL 单实例锁。预测保留计算子进程、CPU 线程限制与超时。

任一子进程退出（包括退出码 0），管理器清除就绪状态，终止其余进程及进程组后代，以非零退出码交给 Docker 的重启策略。SIGTERM/SIGINT 停止时，统一发信号，最多等待 25 秒再强制清理；Compose 停止宽限为 35 秒。重启恢复保持原任务规则，未知邮件与运维动作不自动重发。

```powershell
docker compose exec backend /app/.venv/bin/python -m app.cli.runtime --check
docker compose logs --tail 80 backend
```

完整健康检查同时核对启用进程清单、PID、各消费者心跳及 API `/health/ready`。重启前的旧心跳会被清除。系统管理页仍按消费者展示状态。Docker 的 unhealthy 状态本身不会自动触发重启；子进程退出则由管理器触发容器重启。

### 智能问数消费者与运维开关

`askdata` 消费者承担语义构建与问数执行，默认随 Backend 启动，心跳文件 `/tmp/askdata-worker.heartbeat`（超时 150 秒）。只建表不构建、或只读不提问的部署可以把它从 `BACKEND_WORKERS`／`PLATFORM_WORKERS` 中去掉，其余功能不受影响。

需要临时停止新增构建与问数（例如迁移、扩容或上游模型故障）时，用 `ASKDATA_PAUSED`：

```sh
ASKDATA_PAUSED=on docker compose up -d backend   # 暂停：新提交返回 409，读取与运行中的任务不受影响
ASKDATA_PAUSED= docker compose up -d backend     # 恢复
```

取值 `on`／`true`／`1`／`yes` 视为暂停，大小写不敏感；空值或其他值视为正常。开关只在启动时读取，改完必须重启后端容器。它不删除数据、不改配置、不取消正在运行的任务，暂停期间消费者保留心跳但不领取新任务。

## 验收环境与兼容布局

原独立消费者定义保留在 `compose.workers-standalone.yaml`，供旧验收脚本与故障定位使用；它将 Backend 恢复为仅运行 API。已调整依赖主 Compose 的 AI、执行、预测、前端和工作台验收入口，使它们显式引用此布局。此类旧脚本验证的是独立消费者布局，不能代替合并布局的进程与容器实测。

不要同时运行合并消费者和独立消费者；单实例锁会拒绝重复消费者，管理器会将该失败视为启动失败。

本次合并的回归包括：独立测试库中的真实 API 与六消费者共存、心跳、强制结束 AI 子进程后的整体退出与重启、SIGTERM 正常退出，以及子进程后代清理。另验证既有队列去重、预测子进程、AI 中断恢复、源码去重、报告投递队列与审批复核。Windows 报告测试须设置 `REPORT_FONT_FILE` 指向 `.local/report-font/wqy-zenhei.ttc`。

### 智能问数上线后的回退约束（2026-11-07）

上线前的镜像标记为 `sentinelops-backend:rollback-20261107-stage7`（`152246ea99e3`）与 `sentinelops-frontend:rollback-20261107-stage7`（`fc5b01808ecc`），迁移前的平台库备份在 `.local/backups/ops_platform_20261107_pre_askdata.dump`。回退时注意两点，均已实测：

1. 旧镜像不认识 `askdata` 消费者，直接启动会因 `BACKEND_WORKERS must contain unique supported worker names` 反复重启。代码回退必须同时把两个 worker 变量里的 `askdata` 去掉。
2. 只回退代码不会让就绪探针变绿：平台库已是 `0049_askdata_stage5`，旧代码期望更低版本，`/health/ready` 持续 503（`live` 仍 200，既有业务接口正常，`/api/v1/askdata/*` 返回 404）。可用的回退组合是「旧镜像 + 恢复迁移前备份」，或不回退代码而用 `ASKDATA_PAUSED` 停用新功能。

不通过删除 `askdata` 表回退：那些表与 `public` 业务表同库，删表既不能恢复旧代码预期的版本号，也会丢掉已构建的语义资产。
