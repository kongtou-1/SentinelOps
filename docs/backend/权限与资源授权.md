# 权限与资源授权

## 使用方式

平台保留 Viewer、Operator、Admin 三个角色。导航中的“权限管理”包含“我的权限”（`/access`）和管理员可见的“角色与权限”（`/roles`）。管理员在“角色与权限”按模块调整默认权限；普通用户在“我的权限”查看角色默认与补充授权、批量提交申请。申请选择应用、服务器等资源，以及查看、诊断、日常操作等权限组，默认包含下属资源。期限支持 1、7、30 天和长期，默认 7 天。

管理员在同一页面处理待审批申请、撤销授权和设置资源策略。审批只能维持或缩短期限，不能改目标或扩大权限；不能审批自己的申请。批准从审批时间开始计时。审批结果进入站内待办，不触发新增邮件发送。

“资源策略”默认按指定用户管理。管理员选择一个启用的非管理员用户、资源类型及具体资源，设置“禁止访问”或“跟随原有权限”，确认后保存。页面分别展示已保存策略和当前查看权限；解除单独禁止后仍按角色默认、有效补充授权及全员策略判断，不自动授予额外权限。切换为“所有非管理员”可维护原有普通／受限访问策略。

申请表选定资源后，已拥有的权限组显示“已拥有”并禁选。多资源选择时逐个核验，只向缺少该权限的资源提交；受限资源和下属范围参与判断，角色有查看权限不代表受限对象也已授权。提交前再次刷新权限状态，后端拒绝新申请中已完整拥有的权限组（409）；原请求的幂等重试仍返回原记录。管理员不显示申请按钮。

## 授权规则

- 普通资源接受角色默认权限或有效补充授权；受限资源还要求覆盖对应动作和对象的授权。Admin 保留完整管理能力。
- 指定用户的“禁止访问”优先于该用户的角色默认权限、全局或对象补充授权，对其他用户无影响。应用、服务器的禁止状态覆盖所属下级资源；下级设为“跟随原有权限”不能解除上级的禁止。禁止影响资源的所有受控业务动作、列表及汇总、冻结证据和后台任务权限检查点，管理员账号不能被设置为受限用户。
- 角色默认分配保存在数据库，权限定义与权限组由代码维护。查看、同步、诊断、处理等为业务动作，同一动作的接口共享权限。界面不逐个列出原子权限代码。
- 系统配置、账号、凭据、授权与审批管理，以及现有明确要求 Admin 的复盘操作、强制关闭和跨用户私有会话读取，保留 Admin 限制。私有会话仍只能由所有者修改。
- 服务器范围可覆盖所属容器；应用范围可覆盖所属容器、监测、数据库连接、源码与发布资料。新增和转入资源按当前归属纳入，转出后失效；不沿应用依赖或共享 LLM 绑定扩展。
- 父资源的受限状态作用于下属；单独授予下属访问，不授予父级或同级资源。申请目录仅返回对象名称、类型与标识。
- 列表、分页总数、汇总、搜索、指标、日志、导出、通知和归档采用相同范围过滤。多资源事故和报告必须具备全部相关范围；冻结证据中的资源引用也参与检查。
- 角色变更会撤销全部补充授权，并使待审批申请失效；到期、撤销、禁用后，在后续请求和任务检查点生效。已发出的远程动作继续按原有验证与恢复流程处理。
- 执行发起权限与动作审批分离。资源授权不替代针对具体目标、版本和参数的持久化动作审批。

## 接口

所有路径以 `/api/v1` 为前缀，继续使用 Bearer 访问令牌。完整请求和响应见同目录 `openapi.json`。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /permissions` | 模块、中文权限、权限组、适用范围和固定看板目录 |
| `GET /roles`、`PUT /roles/{code}/permissions` | 查看默认分配、按 `expected_version` 修改 Viewer/Operator |
| `GET /access-targets` | 搜索可申请对象，支持分页和总数 |
| `GET/POST /access-requests` | 查询或批量创建申请 |
| `GET /access-requests/{id}` | 查看申请；普通用户仅能查看自己的申请 |
| `POST /access-requests/{id}/approve`、`reject`、`withdraw` | 批准、拒绝、撤回 |
| `GET /access-grants`、`POST /access-grants/{id}/revoke` | 查看与撤销补充授权 |
| `GET/PUT /access-policies/{kind}/{id}` | 限 Admin；不带 `user_id` 管理全员普通／受限状态，带 `user_id` 管理指定用户的禁止状态 |
| `POST /access/check` | 批量核验动作及对象范围 |

`/me` 保留 `role`、`permissions`，增加 `default_permissions`、`permissions_version` 和 `dashboard_access`。其中 `permissions` 是导航所需的能力集合，不能替代对象授权检查。前端进入页面、重新激活窗口、权限变更或收到 403 时刷新状态，不重试被拒绝的写请求。

资源策略响应包含 `user_id`、`restricted`、`version` 及 `allowed`。指定用户时 `restricted=true` 表示单独禁止，`false` 表示跟随原有权限；`allowed` 表示该用户对当前对象的实际查看权限。全员策略的 `user_id`、`allowed` 均为空。写入继续要求 `expected_version`，版本冲突返回 409。普通用户不能读写其他用户策略；策略审计记录包含操作人和被管理用户。

`POST /access/check` 的条目支持 `include_descendants`，默认 `false` 保持单对象检查；申请前传 `true` 时同时核对应用或服务器的下属范围。仅对象本身的授权不被视为完整拥有下属范围；受限下属、过期或撤销的授权不会误判为已拥有。

申请示例：

```json
{
  "idempotency_key": "一次申请使用的UUID",
  "items": [{
    "bundle_ids": ["applications.view", "diagnosis.run"],
    "resource_kind": "application",
    "resource_id": "目标应用UUID",
    "include_descendants": true
  }],
  "reason": "负责该应用的故障排查",
  "duration_days": 7
}
```

长期申请使用 `duration_days: null`。同一申请可包含多个资源和权限组，一次批准或拒绝；申请保存展开后的权限快照，后续目录变化不会扩大已批准授权。撤销以本次申请在该资源上的权限组为单位执行。

## 数据与升级

迁移版本为 `0034_scoped_access`，新增 `role_permissions`、`access_policies`、`access_requests`、`access_grants`，并为角色增加权限版本。四张表均含 UTC 创建、更新、删除时间及数据库更新时间触发器。审计沿用 `operations_audit_logs`。

`0039_user_resource_policies` 为 `access_policies` 增加可空用户外键和索引，唯一约束按资源类型、资源、用户区分，并对空用户使用 `NULLS NOT DISTINCT` 保持全员策略唯一。已有策略保留为 `user_id=NULL`，不改变现有访问范围；原有时间字段、触发器及版本校验保留。升级 API 和全部业务 worker，避免旧 worker 忽略指定用户的禁止状态。存在指定用户策略时，降级会拒绝执行，需先保存这些策略。

迁移保持原有角色能力和普通资源可见范围，不批量限制现有资源；拆分后的查看权限按原角色初始化。角色管理页面用“部分选中”保留原有权限组合，不自动补齐额外操作。权限组的操作状态按主要动作判断，已有基础查看不会被显示为已拥有诊断或执行能力。

升级前备份数据库和独立主密钥，停止旧 API 与相关 worker，统一构建、迁移并启动新版本。不要混用仍按固定角色判断的旧 worker。沿用 README 的 Compose profiles 和部署步骤，就绪检查要求新迁移版本。

测试必须显式使用名称以 `_test` 结尾的独立数据库。本次开发使用独立自动化测试库与隔离页面验收库；不对业务库执行测试，也不更改远程服务器状态。
