# 智能巡检第一阶段实施与验收

日期：2026-10-29。范围：执行能力与接口契约；页面重组、正式试运行、复制、补检与上线迁移按后续阶段实施。

## 已实现

- 新增统一检查任务：`check_items` 同时支持规则和 Agent，具有稳定检查 ID、启停、异常等级、逐对象/集合范围。定义随任务版本固定，结果独立持久化；没有新增独立检查项 CRUD。
- 固定对象、普通 JSON 与 records 协议发现、cursor/page/offset 分页、对象编号和游标停滞检查。动态列表缺稳定编号、重复编号和重复页不能宣称完成。
- 规则支持原有四类规则及字符串包含/前后缀、集合计数与唯一性；条件组为 AND/OR，保留 unknown 三值逻辑。
- HTTP 状态码和耗时位于统一任务对象的 `facts._http.status_code/elapsed_ms`。明确规则不通过属于业务异常，运行仍可完成。
- 复用现有 `HarnessAdapter`、`DiagnosticGateway`、巡检模型通道和 Python broker。Agent 可以读取 Skill、参考资源、授权 API/数据库、生成/修正 Python，逐对象逐检查项提交结果。
- 增加 `InspectionCheckResult` 和 `InspectionTrace`，保留代码正文、摘要、环境说明、输入证据、输出及错误。结果引用必须属于本检查；业务问题单独保存在结构化 findings 中。
- HTTP 连接与查询配置分离。连接认证加密保存，多个数据源引用同一连接；数据库继续复用 `ServiceDatabase`。
- 数据库可登记带 `:parameter` 的 SELECT，使用 SQLGlot AST 绑定字面值后复用现有表、列、函数授权校验和只读连接。Agent 只传查询标识和允许的参数。发现查询由平台管理排序/分页，不接受自行写入 LIMIT/OFFSET、聚合或 DISTINCT 的对象发现 SQL。
- 查询预览为有权限用户提供少量数据和下一页游标，不创建正式巡检实例，不推进任务进度。它不等同于第二阶段的完整任务试运行。
- 旧 records/agent 任务保持原路径和历史判定；只有使用 `check_items` 的任务采用独立检查项合并语义。没有批量转换旧任务或重判历史结果。

## 状态与预算

`execution_status` 表示一项检查是否完成，`status=pass/fail/unknown` 表示业务结论。业务 fail 不导致整次运行失败；代码/工具错误、Agent 预算跳过和未完成发现导致 partial 或 failed，并保留明确的未完成项。

Agent 失败不会被规则 pass 覆盖。未解决的工具错误不能提交通过结果；代码修正成功后可继续提交。资料不足正常提交 unknown 与执行错误分开记录。

运行详情增加 `summary.coverage`：

| 字段 | 含义 |
| --- | --- |
| discovery_complete | 已确认发现到末页 |
| objects_discovered | 已登记对象数 |
| objects_expected | 总量可靠时的对象数，否则 null |
| expected_is_final | 应检查总量是否已经确定 |
| checks_expected / checks_completed / checks_unfinished | 应执行、完成、未完成检查数 |
| check_counts | pass/fail/unknown 的检查数量 |
| collection_checks | 集合检查数，不混入对象数量 |
| conclusion | 本轮合并结论；未发现完整范围时不能为 pass |
| no_objects | 完整发现后确实无对象，默认 unknown |

固定对象最多 1000 个、单任务最多发现 10000 个。沿用任务总超时、Agent 检查数量预算和单会话 64 次工具/65 次模型请求限制；Agent 默认串行。集合上下文上限 128 KiB，超限明确未完成。Python 继续使用现有无网络、无业务凭据、非 root 临时容器，没有宿主机回退。

首期统一任务的 HTTP 主发现查询限定固定 GET；补充查询可使用已有显式授权的 GET/POST。现有旧自主模式的接口行为不变。正式暂停/恢复语义调整和继续执行属于第三阶段。

## 接口

原有接口路径不变；完整请求和响应以 [OpenAPI](openapi.json) 为准。

| 方法与路径（前缀 /api/v1） | 用途 |
| --- | --- |
| GET/POST `/inspection-http-connections` | 查询/创建共享 HTTP 连接，管理权限 |
| PUT/DELETE `/inspection-http-connections/{id}` | 版本校验更新/引用保护删除 |
| POST `/inspection-data-sources/{id}/preview` | 预览最多 10 条对象，支持登记 SQL 允许的参数覆盖 |
| POST/PUT `/inspection-plans[/{id}]` | 使用 check_items 配置混合任务；自动识别 execution_mode=checks |
| GET `/inspection-runs/{id}/check-results` | 分页读取逐检查项状态、结论、问题及错误 |
| GET `/inspection-runs/{id}/traces` | 分页读取工具、代码及证据轨迹 |

示例为 API 配置形状，不是已创建的业务任务：

```json
{
  "name": "项目材料检查",
  "environment": "test",
  "enabled": false,
  "schedule_kind": "manual",
  "object_mode": "fixed",
  "fixed_objects": [{"id": "project-1", "facts": {"amount": 10}}],
  "check_items": [
    {
      "check_id": "amount",
      "name": "金额非负",
      "kind": "rule",
      "conditions": [
        {"code": "amount", "title": "金额", "kind": "numeric_range", "path": "amount", "minimum": 0, "basis": "金额应非负"}
      ]
    },
    {
      "check_id": "materials",
      "name": "材料一致性",
      "kind": "agent",
      "skill_id": "替换为现有 Skill UUID",
      "source_ids": ["替换为授权查询 UUID"],
      "requirements": "按指定业务标准核对金额和材料；需要计算时使用 Python。"
    }
  ]
}
```

新任务中不再同时传旧 `rules/agent_enabled/related_sources`。`skill_id/source_ids` 必须是实际存在且范围匹配的 UUID。Skill API 增加 `resources`，仅允许 references/assets 下的受限文本文件；scripts 仍使用现有字段。旧编辑请求不传 resources 时保留已有资源。

## 验证与运行状态

自动测试使用独立 `sentinelops_inspection_stage1_test`，连接本机专用测试 PostgreSQL；数据库适配验收使用隔离的 PostgreSQL/MySQL business_test，Python 使用本机专用测试 broker。模拟 Provider 只模拟模型决策，Harness、MCP、HTTP、数据库和 Python 容器均实际执行。

覆盖混合结论、资料不足、预算截断、零对象、300 对象分页、集合检查、跨对象证据拒绝、Python 失败和修正、共享认证脱敏、SQL 字面值绑定、真实两种数据库查询，以及真实 Harness 动态 API/代码/结果提交链。

验证结果：后端巡检、权限、模型通道和结构回归 165 项通过；最后修改后的巡检核心、真实 Harness、迁移结构与旧中心兼容复验 48 项通过。前端 34 个测试文件、242 项通过，包含类型检查的生产构建通过。相关 Python 文件 Ruff 和格式检查通过。OpenAPI、模型元数据契约和前端生成类型已同步。

本机证据：`.local/inspection-stage1-tests.xml`、`.local/inspection-stage1-verified.xml`。外部业务 API 和真实外部模型质量未在本次验收范围内。

## 迁移边界

新增迁移 `0040_inspection_checks`，增加三个表、任务定义与对象状态字段、Skill resources；所有新表带 UTC created_at/updated_at/deleted_at。迁移不更改旧任务模式，不重写已有运行、证据或复核。

本阶段只在独立测试库执行迁移，未更新运行中的业务数据库或 Compose 服务。上线必须先按第三阶段备份、停止相关 worker，并同时升级 backend/worker/前端。就绪检查已随源码要求 0040；不能把新源码直接混入尚未迁移的旧服务。
