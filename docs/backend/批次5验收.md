# 第五批次：LLM 资源监控验收

完成时间：2026-10-02，北京时间 12:16。实施范围仅为第五批次。

## 已实现

- Endpoint 创建、查询、修改、Key 更换、软删除，Viewer / Operator / Admin 权限边界。provider 固定为 DeepSeek，模型名由管理员配置。
- API Key 以 Fernet 加密入库，复用与数据库分离的主密钥；接口和日志不返回 Key 或密文。修改 Key、地址或模型后清除旧探测状态。
- 每 60 秒真实 HTTP 推理、手动推理、15 秒总超时、最多 4 次并发；同一 Endpoint 的探测、修改和删除互斥。禁用停止定时探测，仍允许手动检查。
- 固定短提示词、5 个输出 Token、非流式、关闭思考模式，验证输出为 OK。记录总延迟、HTTP 状态、成功率、错误类别、Token 用量。
- Prometheus 每 15 秒抓取，无网络推理副作用；数据库只保存最近状态，原始时序留在 Prometheus。查询成功率、分类错误率、平均成功推理延迟和 P95，默认 5 分钟窗口；无样本不伪造成功率。
- LLM 可用性、延迟、认证、余额、限流、服务异常、探测过期规则，Endpoint 告警关联与筛选，复用原有 Webhook 幂等、恢复状态和邮件链路。
- `0005_llm_monitoring` 迁移新增 llm_endpoints，并扩展规则和告警的可选引用。全库十张表，包括 Alembic 维护表，均具有 UTC 带时区创建、更新和删除字段及更新触发器。

API 请求字段、规则阈值及启动方式见根目录 README；全部接口已加载至 `http://127.0.0.1:8000/docs`。

## 本地端到端结果

使用 Compose `test-llm` 模拟 Provider，以真实 HTTP 请求进入完整推理、指标及告警链路。自动定时探测已确认执行；每种失败后均恢复为成功。

| HTTP | 分类 | 新告警落库 | 重复通知 | 同一事件恢复 | 新故障/恢复邮件 |
| --- | --- | --- | --- | --- | --- |
| 401 | authentication_failed | 通过 | changed=0 | resolved | 各 1 封 |
| 402 | insufficient_balance | 通过 | changed=0 | resolved | 各 1 封 |
| 429 | rate_limited | 通过 | changed=0 | resolved | 各 1 封 |
| 503 | service_error | 通过 | changed=0 | resolved | 各 1 封 |

邮件验证同时匹配新消息 ID、告警名称、Endpoint ID、错误分类和本次事件起始时间，历史邮件不能通过。全部四个告警事件均已恢复，保留在数据库供复查。

首次汇总检查发现 llm_error_rate 的向量匹配表达式被 Prometheus 拒绝。修正为 `group_left()` 后，已部署新镜像，核对全部 12 个表达式，再补验混合成功/失败请求的实际数据：成功率介于 0 和 1，authentication_failed 错误率大于 0，平均延迟及 P95 均有有效样本。没有重复制造已通过的四类故障。请求计数与 Histogram 重启后重置，由 Prometheus rate 处理。

完整机器可读证据保存在 `.local/batch5-acceptance.json`，包含四个事件 ID、八封新邮件 ID、指标数据和 passed=true。可重复运行 `backend/scripts/accept_llm.py`；脚本结束后恢复模拟 Provider 并禁用测试 Endpoint。
