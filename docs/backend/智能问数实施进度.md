## 阶段 2 实现

迁移 `0045_askdata_semantic_models` 建立版本发布字段、构建步骤与 `askdata.embeddings`（pgvector 512 维、HNSW `vector_cosine_ops`）；`0046_askdata_definitions` 建立 `askdata.definitions`，保存人工修订与认证状态。两张新表均纳入平台 Base/Alembic，包含三个 UTC 时间字段、更新时间触发器和软删除，并进入资源权限范围。收尾全量回归发现 0037—0043 引入的 5 张 public 表缺少 `trg_<table>_updated_at`，另以 `0047_inspection_agent_timestamps` 独立补齐平台既有约定，不改动阶段 2 的问数表结构。

- 构建编排在 `app/services/askdata_build.py`：目录抽取 → 语义编译 → 关系推断 → 指标表达式 → 向量校验 → 内容检查 → 完成。全程绑定 `HostBindings`，每个工作线程独立存储会话，持连接 advisory lock；取消、失败、中断均写入 `builds` 状态、`step`、`error_code` 与 `detail`。
- 版本采用新版本暂存、完成后切换：`draft → ready → publish → retire`。`configurations.active_model_version_id` 是唯一生效版本；构建失败只把新版本置为 `failed`，不改变当前启用版本。
- 向量使用平台 PostgreSQL 与现有本地 `bge-small-zh-v1.5`，由迁移建表和索引，与 `knowledge_chunks` 分开存储；按 `model_version_id` 与 collection 隔离，不执行请求期 DDL。
- 授权采样在 `app/integrations/askdata_sampling.py`：上游 `SELECT * FROM <表> LIMIT 1000` 被重写为**连接授权列 + 50 行上限**的明确列查询，再经既有 SQL 校验器与只读执行器。未授权表和未开启业务读取的连接返回空样本，构建继续依赖结构缓存与人工说明；采样结果不会包含未授权字段。
- 人工修订与认证在 `app/services/askdata_definitions.py`：术语描述／别名、指标表达式与认证状态写入 `definitions` 并回写当前版本的上游对象。构建事务提交后统一沿用上一版本的已认证／人工定义；来源指纹（结构 hash + 源码快照）变化或对象消失时**保留定义并标记待复核**，复核后更新指纹。
- 业务模型界面提供术语、指标、关系的查看与编辑、认证、关系图谱、版本对比和待复核处理；数据目录提供表／字段／主外键／样本值与授权范围浏览。图谱复用 ECharts `graph`，不引入新依赖。

## 阶段 3 实现

阶段 3 未新增迁移、未改动上游源码。复用阶段 1 的 `askdata.conversations`／`runs`／`events` 三张表：执行上下文写入 `kind=context` 事件，后续配置变更不会改写历史结果；运行取消直接写状态，worker 完成时保留取消态；进程重启只把遗留 `running` 置为 `interrupted`，不重跑查询。

- 独立 SQL 校验入口 `app/integrations/askdata_sql.py`。支持 CTE、派生表、子查询、`UNION`／`EXCEPT`／`INTERSECT`、条件表达式、聚合与窗口函数；只把授权列交给优化器，`qualify` 后逐列核对作用域来源，`LIMIT` 统一压到 200 行。拒绝写入型 CTE、递归 CTE、多语句、系统 schema、跨库限定、未授权表字段、`SELECT *`、`OFFSET` 与不在白名单内的函数。诊断和巡检继续调用原 `database_sql.checked_query`，行为不变。
- 统一执行器。`app.services.askdata.database_connector` 增加 `gate="askdata"`，最终查询、值探测与修正查询全部经过平台只读执行器，保留只读账号校验、字段授权、连接锁、5 秒／200 行／128 KiB 限制。`database_readonly.query` 可选返回列类型，数值以字符串保存以保留 decimal 精度；`PlatformDatabase.execute_raw` 跳过语义构建期的采样改写，避免问数 SQL 被误判成表采样。
- 问数编排 `app/services/askdata_query.py`。绑定 `HostBindings`，直接消费上游 `stream_agent_response` 的 step／sql／result／error 事件，映射为不含内部推理的中文步骤标签；注入简体中文回答要求、历史问答与历史 SQL 示例以支持多轮追问；每步检查取消与总体预算（默认 180 秒）。上游链路内部执行 SQL 用于生成答案，平台对最终 SQL 再执行一次受控查询，作为答案、表格、图表与 CSV 共用的唯一展示结果。无 SQL 且回答含澄清语义时标记 `needs_clarification`；口径认证状态取自 `askdata.definitions` 并随证据返回。Kumo 预测与 rerank 首版关闭，`model_config` 为空映射，模型客户端完全由平台 `model_factory` 接管，不逐请求改写环境变量。
- 后台任务。`app/workers/askdata.py` 拆为构建单队列与问数独立线程池（默认并发 2，可用 `ASKDATA_QUERY_CONCURRENCY` 调整），两者分别限流；`claim_run` 使用 `FOR UPDATE SKIP LOCKED`，长任务不占用 API 进程。`ASKDATA_QUERY_BUDGET_SECONDS` 可调整问数预算，诊断与巡检仍用原配置。
- 界面。新增「问数对话」页与 `/askdata/chat`：应用／环境／数据库上下文、私有会话、多轮问答、SSE 执行进度、SQL、结果表格、ECharts 图表、引用依据与认证状态、澄清与失败原因、取消、CSV 导出；SSE 断线从 `latest_seq` 重放，只恢复查看。一级导航同步开放该入口。

- 业务规则 `rules`：`statistical_scope`／`time_semantics`／`unit`／`filter`／`soft_delete`／`status` 六类，带目标、表达式、单位、优先级与启停；启用规则与补充定义通过 `business_context()` 注入问数 `_payload`（evidence 与 acronyms）。
- 敏感数据 `sensitive_fields`：按对象键配置类别与策略（`mask`／`exclude`）、脱敏方式（`keep_prefix`／`keep_suffix`／`hash`／`full`）与参数、采样是否排除。策略在四处生效：采样 SQL 排除列（`sample_statement(excluded=...)`）、采样结果脱敏、模型输入列裁剪、问数结果与 CSV 导出脱敏。
- 补充定义 `supplements`：缩写、别名、上下文三类，带适用对象与别名列表。

### 模型与执行设置

- 推理通道与轻量通道各自绑定已有 Agent 凭据通道（`reasoning_channel_id`／`light_channel_id`），默认同一通道；`model_config()` 生成 `ASKDATA_REASONING_CHANNEL`／`ASKDATA_LIGHT_CHANNEL` 注入 `HostBindings`，`askdata_model` 据此选择 `ChatOpenAI` 客户端，并以 `_UsageRecorder` 回调写 `model_usage`（`source="askdata"`、`purpose="askdata"`）。凭据本身仍由平台加密存储，接口只返回是否已配置。
- 向量模型支持现有本地 `bge-small-zh-v1.5` 与兼容接口；维度可调，变更模型或维度后 `vector_signature` 变化，旧版本在校验时被拒（409「向量模型已变更，请重新构建业务模型」），不会混用旧向量。
- 重排默认关闭；开启需填端点／模型／密钥并通过连接测试（写 `reranker_verified_at`），未通过测试不注入 `RERANK_*` 配置。上游 `auto_ontology/utils/rerank.py` 相应改为按任务解析配置，避免导入期冻结首个任务的端点与密钥。
- 执行预算 `budget_seconds`（30—900，默认 180）写入配置，问数编排优先读配置值。设置写入使用 `expected_version` 乐观并发，冲突返回 409。

### 导入导出（`app/services/askdata_interchange.py`）

- 导出为 JSON 文档（`format="sentinelops.askdata.model"`、`version=1`、上游提交号），包含业务分区、标签、业务规则、敏感字段与补充定义；**不含**连接凭据、查询原始结果与分析记录。
- 导入分两步：`preview` 解析文档并生成逐项计划（`create`／`update`／`skip`／`conflict`，含原因与计数、告警），落 `imports` 记录；`apply` 按 `conflict_policy`（`skip`／`overwrite`）执行并回写报告。冲突项在预览与执行阶段都携带原始 payload，覆盖模式不会写入空对象；导入目标连接仍走 `askdata:manage` 授权核验。

### 部署中修复的缺陷

真实 PostgreSQL 与真实模型通道暴露 6 个问题，确定性测试未覆盖：

1. 适配层从未提交写入，跨线程写列时表行不可见，`catalog_column` 复合外键失败 → `BuildStorage` 增加按事务深度提交的 `commit` 回调。
2. 适配层拒绝多行 `INSERT`，上游批量写外键报 `ontology_single_insert_required` → 支持批量子句并逐行注入 `model_version_id`。
3. 版本作用域把基表包成子查询，PostgreSQL 不再承认「按主键分组、选同表其它列」，`GROUP BY term.id` 报 `GroupingError`，term 读不回、向量为空 → `_expand_group_by` 补回分组列。
4. 检索侧用标准库线程池，丢失 ContextVar 任务绑定，池内向量检索抛「requires an authorized platform task」被吞，候选为空、模型编表名 → 两个检索 agent 改用 `host.ContextThreadPoolExecutor`。
5. 构建只写语义集合、不写数据层集合（上游由 `ingestion_service` 负责），检索无表 → 构建新增 `_index_catalog`，写入 `data_objects_layer`（实测 13 条）。
6. `deepseek-flash` 不支持 `response_format=json_schema`，语义编译首步失败 → 上游 `llm_invoke` 对 DeepSeek 改走 `function_calling` 且不指定 `tool_choice`。
