# 开发源码与运维关联：第三阶段

本阶段完成“正式诊断 → 修复交接 → 修复结果 → 新发布/部署 → 验证记录”的关联。平台保存交接和证据；代码修改、测试、审核、构建和部署继续在现有开发工具中完成。交接记录不产生审批或执行授权。

## 使用流程

1. 在事故详情完成诊断。私有会话中的候选结论先点击“采用”；直接分析产生的已完成正式诊断也可使用。
2. 打开“修复交接”，点击“生成修复交接”，选择正式诊断，填写复现线索和具体验收条件。诊断关联多个服务时，需要选择本次修复服务。没有源码仍可生成材料，并保留缺口。
3. 在详情导出 Markdown 或 JSON，交给开发者或 AI coding。材料包含事故、诊断结论、引用的运行/源码证据、版本身份、路径/行号/片段哈希、知识引用、复现线索和验收条件。源码和说明均按不可信证据处理。
4. 在开发环境修复并运行测试。Admin 在“应用与服务”登记新发布和实际部署；Operator/Admin 在交接详情登记修改说明、完整 Git commit（可选）、测试命令和实际结果，关联新发布及部署。本地目录修复可以用源码快照身份，不要求 Git。
5. 部署后登记证据观测时间、验证方法、数据/证据位置及逐条验收结果。选择“服务恢复”“修复验收通过”“验证未通过”或“尚无结论”。每次验证绑定具体修复结果。

所有角色可查看公开交接和导出；只有 Operator/Admin 可生成、追加修复结果及验证。私有会话权限不变，交接不包含原始聊天、模型配置、密钥或 SDK 提示词。事故关闭后仍可追踪后续代码修复；合并事故保留旧记录只读，在目标事故创建新交接。

## 冻结与校验

生成时再次检查正式诊断的证据引用和源码身份。只保存正式结论引用的证据与知识，不重新读取当前源码，也不等待 Git 或源码 worker。历史诊断没有源码上下文时明确保留缺口。

初始 `packet` 与 SHA256 固定保存。修复结果及验证以追加方式保存，每条带 UUID、登记人、UTC 时间和内容哈希，接口不提供覆盖、删除或任意状态修改。发布身份、源码身份、部署目标和登记时的镜像关联依据随修复结果冻结；以后补充发布资料不会改写旧记录，可以追加一次新的修复记录。

- 已知修复服务时，发布必须属于该服务，且不能选回事故受影响的发布。
- 部署必须属于所选发布，匹配受影响环境和目标。容器重建允许同服务器、同 Compose 项目/服务的新容器；缺少这些明确标识时只接受原容器。LLM Endpoint 必须匹配原目标。
- 修复部署不能早于事故。填写的修复 commit 须与发布中已登记的 Git 身份一致。
- 没有冻结服务绑定时允许后续人工声明发布关系，明确显示关联未由原事故核验；之后保持同一声明服务。
- 验证时间不得在未来、早于事故/修复部署，或超出已登记的部署结束区间。
- “修复验收通过”要求新发布、新部署和完整修复 commit 或可用源码快照身份；镜像身份明确不一致时拒绝该结论。

测试和修复验证均标为 `human_reported`。验证同时保存当时的告警恢复状态和核验证据时间。人工验收通过不自动把 Alert 置为恢复、不改变 Incident 状态、不消费 Approval，也不证明根因永久消除。重启、服务暂时恢复与代码修复验收分别表达。

单份交接（含后续记录）限制 512 KiB，最多 20 条修复结果、50 条验证；超限返回明确错误，不截断证据。事故交接列表分页，默认 10 条。同步过程的网络和文件限制继续沿用第一阶段。

## 接口

| 方法与路径（均以 `/api/v1` 为前缀） | 权限 | 功能 |
| --- | --- | --- |
| POST `/incidents/{id}/repair-handoffs` | repairs:write | 从指定正式诊断生成交接 |
| GET `/incidents/{id}/repair-handoffs` | repairs:read | 分页查询交接，响应含 X-Total-Count |
| GET `/repair-handoffs/{id}` | repairs:read | 查看冻结材料和追加记录 |
| POST `/repair-handoffs/{id}/results` | repairs:write | 追加修复结果及版本关联 |
| POST `/repair-handoffs/{id}/verifications` | repairs:write | 追加指定修复结果的人工验证 |
| GET `/repair-handoffs/{id}/export?format=markdown\|json` | repairs:read | 下载 Markdown 或 JSON |

请求响应字段以 [OpenAPI](openapi.json) 为准。写入交接、结果和验证均追加审计与事故时间线。读操作不创建执行任务。

## 复盘

新复盘的冻结证据新增 `repair_handoff` 记录，包含原始材料、哈希、修复结果和验证记录，覆盖已合并来源事故。模型可以用该记录 ID 引用；提示词明确区分人工验收和资源恢复。事故详情、复盘证据抽屉以及既有 Word/PDF 证据附录均可追溯这些记录。

后续追加验证不会改写已经生成的复盘，需生成新报告才能纳入新资料。报告仍按现有流程人工编辑、审核及显式发送，不自动批准、发送邮件或写入知识库。

## 升级与验收

先备份业务数据库并保留独立解密主密钥。迁移 `0015_repair_handoffs` 新增一张表；包含三个 UTC 时间字段、创建默认值及更新时间触发器。不回填、不改写旧诊断、发布或已审核报告。

```powershell
docker compose build backend frontend
docker compose run --rm migrate
docker compose --profile sources up -d --wait backend frontend source-worker
```

若已启用 AI/执行/复盘 worker，同步更新对应后端镜像。现有可选目录挂载不变，无源码时核心服务仍可运行。

隔离验收脚本为 [accept_repair_handoff.py](../../backend/scripts/accept_repair_handoff.py)，仅允许运行于 `ops_platform_repairs_acceptance_test`。它构建测试服务的故障/修复镜像，通过真实 HTTP 503 → 200、真实 Harness/MCP 与模拟 Provider 验证交接；不代表真实 DeepSeek 或生产故障诊断质量。脚本保存复盘证据投影测试快照，明确标为测试材料，不是已审核业务报告。实际复盘生成、编辑审核、Word/PDF 与邮件队列继续执行回归测试。

验收记录见[第三阶段验收](开发源码与运维关联第三阶段验收.md)。
