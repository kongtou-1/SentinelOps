# SentinelOps 项目组织与本机迁移

后端采用 FastAPI 模块化单体。项目名称为 SentinelOps，工作目录以当前检出的项目根目录为准，Python 包保留 `app`，后端项目名为 `sentinelops-backend`。下方本机迁移记录中的绝对路径是当时的历史记录。

当前容器部署采用 [Backend 合并运行方案](容器合并与部署.md)：API 与七类后台消费者共享容器，审批执行和巡检沙箱保持独立。下文历史验收与切换记录保留当时状态。

## 后端目录

| 目录 | 职责 |
| --- | --- |
| `app/main.py` | 创建应用、生命周期、异常处理 |
| `app/api/router.py`、`app/api/routes` | 统一注册与按业务划分的 HTTP 接口 |
| `app/api/dependencies.py` | 请求认证、权限和 Session 注入 |
| `app/core` | 配置、基础路径、密码与 JWT、权限定义、密钥与凭据加解密、服务令牌校验 |
| `app/db` | 唯一 Base、时间字段、Engine、Session |
| `app/models`、`app/schemas` | ORM 模型与数据结构 |
| `app/services` | 业务流程、校验、事务及响应数据准备 |
| `app/services/records.py`、`app/repositories/records.py` | 共用的未删除记录查询与既有简单保存操作 |
| `app/repositories` | 查询构建、数据库读取与写入；不提交业务事务 |
| `app/integrations` | SSH、Prometheus、Harness、Git 与凭据辅助、诊断网关、只读 Docker 采集器 |
| `app/workers` | 持久化任务消费、调度与恢复 |
| `app/cli`、`app/utils`、`app/skills` | 管理入口、通用脱敏、现有只读诊断 Skill |

服务层不导入 API。仓储不导入 FastAPI 或上层业务模块；事务提交、回滚、锁的作用范围保持原有顺序。各层按认证、资源、监控告警、LLM、预测、事故、诊断、知识库、审批执行、复盘、源码、修复交接及市场归类。

所有 ORM 模型共享 `app.db.base.Base`，在 `app.models` 完整注册。类继续使用 `app.models` 作为公开 Python 模块身份：这既保持原来的导入/序列化身份，也保持 SQLAlchemy 原有的写入排序。仅修改类所在文件会改变该排序，从而使无显式 relationship 的跨表写入出现外键错误。

## 可复用能力的归属

共用函数从所属模块直接导入，不通过资源 CRUD、监控配置或 SSH 模块转导入。

| 能力 | 导入位置 |
| --- | --- |
| 读取密钥、取得原有凭据加解密器 | `app.core.secrets` 的 `file_secret`、`cipher` |
| 服务 Bearer 令牌校验 | `app.core.service_auth.service_authorization` |
| 记录查询与简单保存 | `app.services.records` 的 `active_record`、`save` |
| Prometheus HTTP 请求 | `app.integrations.prometheus.prometheus` |
| 主机/容器/LLM 指标表达式、采样可用性 | `app.services.monitoring.metrics` |
| 主机与容器指标读取 | `app.services.resources.metrics` |
| LLM 展示状态计算 | `app.services.llm.status.endpoint_status` |
| 从采集数据提取容器 ID | `app.utils.docker.docker_identifier` |
| 报告及修复交接的 JSON 编码、摘要 | `app.utils.canonical_json` 的 `encoded`、`digest` |

`active_record` 排除软删除记录，不提交事务，也不替代业务权限和范围检查。`save` 保留原有 add、commit、失败 rollback、成功 refresh 顺序，只用于已经采用该保存方式的简单业务路径；复杂流程的事务继续由原业务服务控制。仓储使用传入的 Session，不自行提交。

指标表达式与数据可用性处理独立于资源写入和规则发布。LLM 指标继续保留原有响应结构与非有限值处理。LLM 状态计算独立于探测调度，服务监测自己的 `paused`、新鲜度语义保持不变。

容器采集使用的宽容 ID 提取与执行 Skill 中的严格校验保持分离；执行必须使用 `app.services.executions.skills.docker_identifier`。报告摘要继续拒绝 NaN/Infinity，不替换审批绑定的摘要算法，也不重新计算历史哈希。

`tests/test_project_structure.py` 检查共用模块的依赖方向及旧导入路径，并识别绝对与相对导入。实施和验证结果见 [后端复用模块整理实施与验收](后端复用模块整理实施与验收.md)。

## 启动与验证

API 入口仍为 `uvicorn app.main:app`。后台入口为 `app.workers.predictions`、`app.workers.sources`、`app.workers.ai`、`app.workers.executions`、`app.workers.reports`；会话消费由 AI worker 调用 `app.workers.conversations`。管理员初始化入口为 `python -m app.cli.bootstrap`。

预测计算子进程、Harness 子进程、Git 凭据辅助脚本及采集器文件位置均使用整理后的模块路径；文件资源从 `core.config.BACKEND_ROOT` 定位。

使用 uv 和现有锁文件安装依赖。pytest 只可连接独立测试库；本机 PDF/Word 测试需通过 `REPORT_FONT_FILE` 指向文泉驿字体，容器内沿用原字体路径。前端执行类型检查、Vitest 和构建。

`tests/test_project_structure.py` 比对完整 API 契约、当前 42 个模型的元数据和依赖方向。数据库迁移历史不变；数据库名称、账号、JWT 声明和密钥不变。后文 2026-10-15 验收记录中的 39 个模型是当时的数量。

## 迁移与回退

八项设计补全新增独立 `operations-worker` 和迁移 `0025_service_objectives` 至 `0031_data_cost_governance`，当前就绪版本为后者。新增模型按 operations/notifications/evaluation/improvements/platform/governance 业务拆分；新表及维护表均保留 UTC 时间和更新时间触发器。新增 `notification_config`、`archives` 持久化卷，交接脚本按实际 Compose 服务与全表指纹检查。具体逐阶段启用、验收和清理后的恢复限制见[实施记录](../project/八项设计补全实施与验收.md)。以下改名与切换内容为历史记录，不作为本次部署路径或版本要求。

迁移前的代码、OpenAPI、模型元数据、迁移文件哈希、运行资源清单及数据库备份保存在本机 `.local/sentinelops-refactor/`。该目录含本机配置备份，不应提交或对外分享。

主平台从 `contest-ops` 迁到 `sentinelops`；实测环境从 `contest-testlab` 迁到 `sentinelops-testlab`。九个卷的后缀保持：`postgres_data`、`prometheus_data`、`alertmanager_data`、`mailpit_data`、`backend_secrets`、`prometheus_secrets`、`alertmanager_secrets`、`platform_rules`、`source_store`。

在维护窗口停止旧项目的流量和写入，检查无正在执行的运维动作，完成数据库备份，再离线复制全部卷并比较内容摘要和权限。新旧环境不同时写入同一组卷。新环境启动前比较数据库逐表数量与摘要；启动后重新同步容器，更新当前 testlab 资源、预测任务及部署关联。

新容器拥有新的 Docker ID。旧部署通过已有 API 结束，再建立新部署；旧审批不移植到新容器。历史源码快照、事故、审批、发布和审计保留原始值；当前操作说明使用新名称。

验收失败时停止新项目，从保留的旧容器、镜像、卷和配置恢复。验收通过前不删除旧目录、旧卷或旧镜像，不执行 `down -v` 或全局清理。

## 已发现的原有测试问题

迁移前完整测试为 586 通过、13 失败，其中 12 项因 Windows 缺少导出字体，1 项因表清单未包含既有的 `llm_service_bindings`。补齐字体及表清单后，发现原 `0020_llm_service_bindings` 迁移没有建立其他表使用的更新时间触发器。此次不更改数据库结构和迁移历史，该问题单独记录；ORM 原有的 `updated_at` 更新行为保留。

强制关闭报告的测试样例同时补齐现有报告数据结构要求的 `evidence_ids` 字段，应用行为不变。实际最终测试和切换结果记录在本机验收文件及本文的验收记录中。

另确认原源码部署接口对 LLM Endpoint 分支访问了不存在的 `server_id`，该分支原本会返回 500；原始代码备份中也存在相同问题。本次未改动这一业务逻辑，隔离闭环使用已有的容器部署分支。

### 验收后的旧容器清理

用户随后明确授权删除旧容器。已删除旧主平台的 15 个容器和旧 testlab 的 3 个容器，保留全部原镜像、九个旧卷和旧目录；新平台就绪检查正常。删除前的容器配置与末尾日志保存在新目录 `.local/sentinelops-refactor/`，配置文件为 `removed-containers-inspect.json`，含本机敏感配置，不应提交或分享。
